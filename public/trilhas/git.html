Git Engineering

Ideia central

Para o básico, Git é histórico. Para o intermediário, é colaboração. Para o avançado, é automação, qualidade e segurança. Para o sênior, Git é parte da arquitetura de entrega de software.

Objetivo

Trilha progressiva por nível

Evolução do básico ao sênior com resultado esperado em cada fase de maturidade.

Senioridade

Nível básico

Fundamentos

Entender repositório, commit, branch, remote, clone, push, pull, fetch, add, status, log e diff.

  • Criar branch local.
  • Fazer commits pequenos.
  • Enviar para remoto.
  • Abrir PR/MR simples.
  • Evitar commits gigantes e cópias manuais como projeto-final-v2.zip.

Nível intermediário

Time real

Trabalhar com branches, PR/MR, conflitos, merge, rebase, squash, code review e evidência de teste.

  • Resolver conflitos sem apagar regra do colega.
  • Atualizar branch com frequência.
  • Escrever PRs pequenas e revisáveis.
  • Usar templates e relacionar task/issue.

Nível avançado

Git interno

Dominar modelo interno, HEAD, refs, reset, revert, restore, stash, cherry-pick, bisect, hooks e automação.

  • Entender por que rebase muda hashes.
  • Usar revert em histórico compartilhado.
  • Usar bisect para localizar regressão.
  • Automatizar validações em hooks e pipelines.

Nível sênior

Governança

Definir políticas, permissões, branching, releases, CODEOWNERS, monorepo/multirepo, GitOps e auditoria.

  • Escolher fluxo por contexto.
  • Configurar branch protection.
  • Versionar contratos e infraestrutura.
  • Medir saúde do fluxo de desenvolvimento.
  • Migrar plataformas com risco controlado.

Fundamentos essenciais do Git

Controle de versão, estados principais e comandos obrigatórios para operar com segurança.

Git Core

O que é controle de versão

Controle de versão registra mudanças em arquivos ao longo do tempo. Em software, isso permite saber quem alterou, quando alterou, por que alterou e como comparar ou voltar para estados anteriores.

RepositórioLocal onde o histórico do projeto é armazenado.
CommitSnapshot versionado com mensagem, autor, data e referência ao estado do projeto.
BranchPonteiro leve e móvel para uma linha de desenvolvimento.
TagMarcador para versões ou pontos importantes do histórico.
RemoteRepositório remoto usado para colaboração, como origin.
Fetch/Pull/PushOperações para buscar, integrar e enviar mudanças ao remoto.

Estados principais do Git

Área Função
Working Directory Onde você edita arquivos localmente.
Staging Area / Index Área de preparação do próximo commit.
Repository Banco local de commits, branches, tags e objetos Git.

Fluxo mental básico

# edita arquivos
git status

# adiciona mudanças ao staging
git add arquivo.java

# cria snapshot versionado
git commit -m "feat: add customer validation"

# envia para o remoto
git push origin minha-branch

Comandos básicos obrigatórios

git init
git clone <url>
git status
git add .
git commit -m "mensagem"
git log
git diff
git branch
git switch -c minha-branch
git switch main
git pull
git push

Erro comum

git add não envia arquivo para GitHub, GitLab ou Azure Repos. Ele apenas prepara a mudança no staging para o próximo commit local.

Nível intermediário - colaboração e fluxo real

Branches, merge, rebase, conflitos e Pull/Merge Requests em times profissionais.

Colaboração

Branches

Uma branch é um ponteiro leve e móvel para um commit. Ao criar uma branch, o Git cria uma nova referência; conforme commits são feitos, esse ponteiro avança.

git switch -c feature/customer-api
git add .
git commit -m "feat(customer): create customer endpoint"
git push origin feature/customer-api
  • Use nomes claros: feature/, bugfix/, hotfix/ e release/.
  • Evite branches longas demais.
  • Atualize sua branch com frequência.
  • Não trabalhe diretamente na main/master.
  • Abra PR/MR pequena e revisável.

Merge vs rebase

Técnica Como funciona Quando usar Risco
Merge Preserva a linha histórica original e pode criar commit de merge. Quando você quer preservar claramente o histórico de integração. Histórico pode ficar mais ruidoso em times com muitas branches.
Rebase Reaplica commits de uma branch sobre outra base. Quando você quer atualizar sua branch com a main e manter histórico mais linear. Reescreve histórico; não use em commits compartilhados sem alinhamento.
Squash merge Condensa vários commits em um único commit na branch principal. Quando a PR tem muitos commits intermediários sem valor histórico. Pode perder granularidade se usado sem critério.

Fluxos de atualização

# merge
git switch main
git pull
git merge feature/customer-api

# rebase
git switch feature/customer-api
git fetch origin
git rebase origin/main

Conflitos de merge

git status
# abrir arquivos com conflito
# resolver manualmente
git add arquivo-com-conflito.java
git rebase --continue
# ou
git commit

Não faça

  • Aceitar ours/theirs sem entender.
  • Resolver conflito apagando regra de negócio do colega.
  • Resolver conflito sem rodar testes.
  • Fazer merge gigante depois de semanas de branch parada.

Modelo de PR/MR

## Objetivo
Implementar validação de cliente antes da criação do pedido.

## Alterações
- Adicionado CustomerValidator
- Criado teste unitário para documento inválido
- Ajustado retorno 400 no controller

## Como testar
1. Rodar `mvn test`
2. Chamar POST /orders com customerId inválido

## Riscos
Baixo. Impacta apenas fluxo de criação de pedido.

Nível avançado - Git interno, qualidade e recuperação

Modelo interno, HEAD, reset, revert, restore, stash, cherry-pick, bisect e hooks.

Git Internals

Modelo interno

Git trabalha com objetos como blobs, trees e commits. Blobs representam conteúdo de arquivos, trees representam diretórios e commits apontam para uma tree com metadados, autor, mensagem e commit pai.

BlobConteúdo de arquivo versionado.
TreeEstrutura de diretórios e ponteiros para blobs/trees.
CommitObjeto que aponta para a tree, pais e metadados.
RefReferência nomeada como branch ou tag.
HEADPonteiro para a posição atual no histórico.
HashIdentificador derivado do conteúdo e metadados do objeto.

HEAD, refs e detached HEAD

HEAD -> feature/customer-api -> commit abc123

# detached HEAD
HEAD -> commit abc123

Detached HEAD é útil para inspeção, mas perigoso para trabalho contínuo se você não criar uma branch antes de continuar.

Reset, revert e restore

Comando Função Uso seguro
git revert Cria um novo commit desfazendo outro commit. Use em produção, branches compartilhadas e histórico corporativo.
git reset Move o ponteiro da branch; pode alterar staging e working directory. Use com cuidado; reset --hard pode descartar alterações locais.
git restore Restaura arquivos no working directory ou staging. Use para desfazer mudanças locais específicas. 
git revert <commit>

git reset --soft HEAD~1
git reset --mixed HEAD~1
git reset --hard HEAD~1

git restore arquivo.java
git restore --staged arquivo.java

Ferramentas avançadas

Stash

Guarda mudanças temporariamente sem commit: git stash, git pull, git stash pop. Não use como lixeira permanente.

Cherry-pick

Aplica commit específico em outra branch. Útil para hotfix, mas pode duplicar mudanças e gerar conflitos futuros.

Bisect

Ajuda a descobrir qual commit introduziu um bug. Muito valorizado em bases grandes.

Hooks

Scripts acionados por eventos do Git, como pre-commit. Bons para lint, testes rápidos, padrões de mensagem e bloqueio de segredos.

Reflog

Histórico local de movimentos de HEAD e refs. Útil para recuperar commits ou estados perdidos localmente.

Tags

Marcam versões/release points, como v1.2.3, e sustentam rastreabilidade de releases.

git stash
git stash pop

git cherry-pick <commit>

git bisect start
git bisect bad
git bisect good <commit-antigo>

git reflog
git tag v1.0.0

Critério sênior

Hooks locais ajudam, mas não substituem validação no servidor ou pipeline, porque hooks locais podem ser ignorados. O controle real deve estar no CI/CD e nas políticas da plataforma.

Convenções profissionais de commits

Conventional Commits, SemVer, changelog e automação de releases.

Commits & SemVer

Conventional Commits

Conventional Commits define uma convenção leve para mensagens de commit com significado humano e automatizável. A estrutura base é tipo, escopo opcional e descrição.

feat(order): add order creation endpoint
fix(payment): handle null authorization code
test(customer): cover invalid document scenario
refactor(order): extract validation service
docs(readme): add local setup instructions
ci(pipeline): add integration test stage

# breaking change no cabeçalho
feat(api)!: change customer response contract

# breaking change no corpo
feat(api): change customer response contract

BREAKING CHANGE: field documentNumber was renamed to taxId

SemVer

Semantic Versioning usa o formato MAJOR.MINOR.PATCH. Correções compatíveis incrementam PATCH, funcionalidades compatíveis incrementam MINOR e mudanças incompatíveis incrementam MAJOR.

1.2.3
| | +-- patch: correção de bug compatível
| +---- minor: nova funcionalidade compatível
+------ major: mudança incompatível
BibliotecasVersionamento claro para dependências Maven, npm e SDKs.
APIs públicasControle de breaking changes e contratos consumidos por outros times.
ReleasesTags, changelog e artefatos versionados com rastreabilidade.
AutomaçãoGeração de changelog e release notes a partir de commits padronizados.

Regra prática

Commit bom explica intenção e impacto. Commits como ajustes, correções diversas ou final não ajudam auditoria, revisão nem rollback.

Estratégias de branching

GitHub Flow, GitFlow, Trunk-Based Development e release branches por contexto.

Branching Strategy
Estratégia Modelo Indicado para Atenção
GitHub Flow main + feature/* + pull request + merge na main. Times pequenos/médios, deploy contínuo, produto web, branches curtas e CI forte. A main precisa estar sempre pronta para deploy.
GitFlow main, develop, feature/*, release/* e hotfix/*. Produtos com releases planejadas, homologação formal, ciclos longos e software instalável. Pode gerar branches longas, muitos merges e maior custo operacional.
Trunk-Based Development Colaboração em main/trunk com branches muito curtas, feature flags e CI forte. Times maduros, SaaS, microserviços, alta frequência de entrega e testes confiáveis. Exige testes rápidos, pipeline robusto, rollback/fix-forward e disciplina.
Release branches Branches como release/1.8.x para estabilizar versão enquanto main evolui. Mobile, sistemas embarcados, on-premise, APIs com contrato formal e sistemas regulados. Exige política clara de cherry-pick, hotfix, tags e fim de vida.

Exemplos de estrutura

# GitHub Flow
main
  └── feature/*
       └── pull request
            └── merge na main

# GitFlow
main
develop
feature/*
release/*
hotfix/*

# Release branch
main
release/1.8.x
hotfix/1.8.1

Decisão sênior

Escolher GitFlow para um time que precisa de deploy contínuo cria atrito. Escolher trunk-based sem testes suficientes cria risco. A estratégia deve refletir maturidade do time, frequência de entrega, compliance, criticidade e automação disponível.

Plataformas: GitHub, GitLab, Bitbucket, Azure Repos e alternativas

Forjas Git modernas não substituem o Git; adicionam colaboração, automação, segurança e governança.

Platforms

GitHub

Forte em colaboração, open source, Pull Requests, GitHub Actions, Packages, Dependabot, CodeQL, secret scanning, branch protection, environments e releases.

GitLab

Plataforma DevSecOps integrada com Git, Merge Requests, CI/CD, runners, registries, environments, security scanning, protected branches, approvals e self-managed.

Bitbucket

Plataforma Atlassian com integração forte com Jira, Pull Requests, branch permissions e Bitbucket Pipelines.

Azure Repos

Parte do Azure DevOps, com Git repos, PRs, branch policies, permissões, Azure Pipelines, Boards, Artifacts e Test Plans.

Gitea

Solução self-hosted leve para Git hosting, colaboração, code review, package registry e CI/CD.

Forgejo e SourceHut

Forgejo prioriza software livre, privacidade e controle. SourceHut segue fluxo minimalista com patches e mailing lists.

Quando escolher

Plataforma Melhor contexto
GitHub Projetos open source, ecossistema amplo, colaboração por PR, Actions e GitHub Enterprise.
GitLab Empresas que querem DevSecOps integrado, self-host, CI/CD centralizado e governança forte.
Bitbucket Empresas que usam Jira intensivamente e querem rastreabilidade issue -> branch -> PR -> deploy.
Azure Repos Times em Azure DevOps, Boards/Pipelines e ambientes Microsoft/Azure.
Gitea Laboratórios internos, times pequenos, baixo custo operacional e self-host simples.
Forgejo Organizações com foco em soberania tecnológica, software livre e controle da infraestrutura.
SourceHut Projetos open source tradicionais, fluxo por patches, listas de e-mail e estilo kernel/Linux.

Comparação prática das plataformas

Critérios objetivos para escolher plataforma por contexto, não por preferência pessoal.

Comparativo
Plataforma Melhor para Pontos fortes Atenção
GitHub Open source, comunidade e produto moderno. PRs, Actions, Security, Copilot, ecossistema e GitHub Enterprise. Recursos avançados podem depender de plano pago.
GitLab DevSecOps completo. CI/CD nativo, self-host, segurança, governança e monorepo pipelines. Administração pode ser mais complexa.
Bitbucket Times Atlassian. Jira, Pipelines, PRs e branch permissions. Ecossistema menor que GitHub.
Azure Repos Empresas Microsoft/Azure. Azure Boards, Azure Pipelines, políticas corporativas e permissões. Menos usado em open source.
Gitea Self-host leve. Simples, leve, Git hosting e CI/CD. Menos recursos enterprise nativos.
Forgejo Software livre e self-host. Privacidade, controle e comunidade livre. Ecossistema menor.
SourceHut Patches e mailing lists. Fluxo simples, textual e open source clássico. Curva cultural diferente para quem vem de PRs.

Critério de seleção

A escolha deve considerar governança, integração com backlog, CI/CD, compliance, segurança, self-host, custo, maturidade do time e capacidade operacional.

CI/CD aplicado ao versionamento

Como Git aciona qualidade, testes, build, scan, artefato e deploy controlado.

CI/CD

Em times maduros, cada push ou PR pode acionar um fluxo: commit -> pipeline -> testes -> build -> scan -> artefato -> deploy.

GitHub Actions - exemplo Java/Spring

name: Java CI

on:
  pull_request:
    branches: [ "main" ]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - name: Set up Java
        uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: 21

      - name: Run tests
        run: ./mvnw test

GitLab CI/CD - exemplo equivalente

stages:
  - test
  - build

test:
  stage: test
  image: eclipse-temurin:21
  script:
    - ./mvnw test

build:
  stage: build
  image: eclipse-temurin:21
  script:
    - ./mvnw package -DskipTests

Pipeline profissional deve validar

BuildCompilação ou empacotamento confiável.
TestesUnitários, integração, contrato e E2E quando necessário.
Lint/formatPadrões automáticos antes do merge.
Análise estáticaQualidade, bugs e vulnerabilidades.
DependênciasSCA, CVEs e atualização automatizada.
Imagem DockerBuild, scan e publicação em registry.
ArtefatosPublicação rastreável por commit/tag.
DeployAmbiente controlado com aprovação, rollback e evidência.

Segurança em versionamento

Branch protection, segredos, .gitignore, permissões e recuperação de vazamentos.

Security

Proteção de branches

  • Bloquear push direto em main/master/develop/release/production.
  • Exigir PR/MR.
  • Exigir aprovação e aprovação de CODEOWNERS.
  • Exigir pipeline verde e branch atualizada.
  • Bloquear force push e deleção.
  • Exigir commits assinados em contextos sensíveis.
  • Exigir scan de segurança antes do merge.

Segredos que nunca devem ser commitados

SenhaCredenciais humanas ou técnicas.
TokenTokens de API, Git, cloud, CI/CD e serviços externos.
API keyChaves de provedores e integrações.
Private keyChaves SSH, certificados e chaves privadas.
.env realVariáveis de ambiente com segredo.
Connection stringStrings com usuário, senha e host sensível.

Boas práticas

  • Usar .env.example, nunca .env real.
  • Usar secrets da plataforma.
  • Rotacionar credenciais vazadas.
  • Remover segredo do histórico quando necessário.
  • Usar .gitignore, secret scanning, pre-commit hooks, vault ou secret manager.
  • Separar service accounts de contas humanas e aplicar menor privilégio possível.

Erro comum

Commitar target/, node_modules/, .env, builds e arquivos gerados aumenta risco, ruído, tamanho do repositório e vazamento de informação.

CODEOWNERS não é burocracia: garante que áreas críticas sejam revisadas por pessoas com contexto técnico.

Estratégia de permissões

Papel Permissão
Admin/Owner Configura repositório, permissões, políticas e integrações críticas.

Developer Cria branches, PRs/MRs e contribui no código.

  • Poucas pessoas com admin.
  • Ninguém faz push direto em produção.

  • Auditoria periódica de acesso.

Boas práticas de code review

Revisão sênior valida qualidade, risco, manutenção, contrato e operação.

Code Review

Em nível sênior, code review não é procurar espaço em branco. É validar se a solução resolve o problema correto, reduz risco e mantém o sistema sustentável.

Checklist do reviewer

  • A solução resolve o problema correto?
  • Há teste cobrindo regra de negócio?
  • O código é legível?
  • A alteração quebra contrato de API?
  • Há impacto em performance?
  • Há impacto em segurança?
  • Há risco de concorrência?
  • Há alteração de schema?
  • Há rollback possível?
  • Logs expõem dados sensíveis?
  • A PR está pequena o suficiente?
  • O pipeline passou?

Checklist de quem abre PR/MR

  • Título claro e Conventional Commit quando possível.
  • Contexto do problema.
  • Solução aplicada.
  • Testes executados.
  • Impacto e riscos.
  • Prints/logs quando útil.
  • Link para issue, task ou história.
  • Checklist de breaking changes e rollback.

Descrição boa de PR

## Contexto
Pedidos estavam sendo criados sem validar documento do cliente.

## Solução
Adicionado CustomerDocumentValidator antes da criação do pedido.

## Testes
- CustomerDocumentValidatorTest
- OrderServiceTest
- mvn test executado localmente

## Impacto
Fluxo POST /orders passa a retornar 400 para documento inválido.

Monorepo vs multirepo

Como escolher estrutura de repositórios considerando autonomia, CI/CD, permissões e acoplamento.

Repo Strategy

Multirepo

Cada serviço/projeto tem seu próprio repositório.

Vantagens

  • Isolamento.
  • Permissões por serviço.
  • Pipelines menores.
  • Release independente.
  • Menor complexidade inicial.

Desvantagens

  • Difícil padronizar.
  • Duplicação de configuração.
  • Mudanças cross-service exigem várias PRs.
  • Gestão de dependências mais complexa.

Monorepo

Vários projetos dentro de um único repositório.

Vantagens

  • Visão única.
  • Refatorações transversais.
  • Padronização.
  • Compartilhamento de libs.
  • Histórico centralizado.

Desvantagens

  • Pipelines mais complexos.
  • Permissões mais difíceis.
  • Build pode ficar pesado.
  • Exige tooling forte.
  • Exige path filters, owners e cache.

Exemplo de monorepo

.
├── apps/
│   ├── web/
│   └── admin/
├── services/
│   ├── ms-auth/
│   ├── ms-orders/

Git em arquitetura moderna e GitOps

O repositório como fonte de verdade para código, infraestrutura, políticas, workflows e auditoria.

GitOps

Git como base para CI/CD

Em times maduros, o repositório vira o ponto de entrada da engenharia: código, infraestrutura, documentação, políticas, workflows, releases e evidências de auditoria.

commit -> pipeline -> testes -> build -> scan -> artefato -> deploy

GitOps

GitOps usa Git como fonte de verdade para o estado desejado de infraestrutura e aplicações.

Alteração em manifest Kubernetes
        ↓
Pull Request
        ↓
Review + pipeline
        ↓
Merge na main
        ↓
Argo CD / Flux aplica no cluster
  • Branch protection obrigatória.
  • PR obrigatória.
  • Auditoria por commit.
  • Rollback via commit.
  • Separação por ambientes.
  • Segredos fora do Git.
  • Revisão de infraestrutura como código.

Risco

GitOps sem proteção de branch, validação de manifest, revisão de IaC e gestão adequada de segredos transforma Git em ponto único de propagação de erro.

Erros comuns por nível

Falhas que impedem evolução de maturidade e quebram segurança do fluxo.

Anti-patterns

Iniciante

  • Fazer tudo na main.
  • Não usar git status.
  • Commits gigantes.
  • Mensagens ruins.
  • Subir .env.
  • Confundir pull com fetch.
  • Resolver conflito sem testar.

Intermediário

  • Rebase incorreto em branch compartilhada.
  • PR grande demais.
  • Force push sem cuidado.
  • Não atualizar branch.
  • Usar merge sem entender histórico.
  • Não usar tags/releases.

Avançado

  • Pipeline lento e sem cache.
  • Ausência de branch protection.
  • CODEOWNERS mal configurado.
  • Falta de política de secrets.
  • Monorepo sem estratégia.
  • Releases manuais sem rastreabilidade.

Sênior

  • GitFlow onde deploy contínuo seria melhor.
  • Trunk-based sem testes suficientes.
  • Permissões excessivas.
  • Falta de rollback.
  • Falta de auditoria.
  • Não versionar contratos.
  • Não definir breaking changes.
  • Não medir saúde do fluxo.

Plano de estudo sugerido

Roadmap de 36 semanas com entregas práticas por fase para sair do básico e chegar à maturidade sênior.

Roadmap 36 semanas

Fase 1 - Fundamentos

Sem 1-4

Estudar: Git, repositório local, commit, branch, remote, push, pull, fetch, .gitignore e GitHub básico.

Praticar: git init, add, commit, log, branch, switch, merge, remote e push.

Entrega: repositório com README, branches e commits organizados.

Fase 2 - Colaboração

Sem 5-10

Estudar: Pull Request, Merge Request, code review, conflitos, rebase, squash merge, templates e issues.

Praticar: criar PR, revisar PR, simular conflito, resolver conflito, usar rebase e squash.

Entrega: projeto com duas branches, PR documentada e evidência de teste.

Fase 3 - Histórico e recuperação

Sem 11-16

Estudar: reset, revert, restore, stash, reflog, cherry-pick, bisect e tags.

Praticar: reverter commit, recuperar alteração, aplicar cherry-pick e localizar bug com bisect.

Entrega: simular bug introduzido e encontrar o commit causador com git bisect.

Fase 4 - Automação

Sem 17-22

Estudar: GitHub Actions, GitLab CI/CD, Azure Pipelines/Bitbucket Pipelines, checks obrigatórios, testes, build, deploy, cache e matrix builds.

Praticar: pipeline de PR com testes e build.

Entrega: pipeline obrigatório rodando testes antes do merge.

Fase 5 - Segurança e governança

Sem 23-28

Estudar: secret scanning, code scanning, Dependabot, branch protection, CODEOWNERS, signed commits, permissões, tokens e .env seguro.

Praticar: proteger branch, exigir PR, exigir pipeline e configurar CODEOWNERS.

Entrega: repositório com branch protegida, PR obrigatória, pipeline obrigatório, CODEOWNERS e sem segredos.

Fase 6 - Nível sênior

Sem 29-36

Estudar: branching strategy, trunk-based, GitFlow, release management, SemVer, Conventional Commits, monorepo, GitOps, governança, auditoria e migração.

Praticar: definir política completa de versionamento para projeto real.

Entrega: documento de governança e repositório final com CI/CD, segurança, release e documentação.

Resumo final da trilha

Síntese prática para fixar a evolução de maturidade em Git e versionamento.

Síntese

Ordem mental de evolução

  1. Entender controle de versão.
  2. Dominar working directory, staging e repository.
  3. Criar commits pequenos e mensagens úteis.
  4. Trabalhar com branches e remotes.
  5. Abrir PR/MR com evidência.
  6. Resolver conflitos com teste.
  7. Entender merge, rebase e squash.
  8. Dominar reset, revert, restore, stash, cherry-pick e bisect.
  9. Padronizar Conventional Commits e SemVer.
  10. Configurar CI/CD e branch protection.
  11. Aplicar segurança, CODEOWNERS e permissões.
  12. Escolher branching strategy por contexto.
  13. Versionar contratos, infraestrutura e ADRs.
  14. Evoluir para GitOps e governança de entrega.

Diferença real do sênior

O profissional sênior não apenas usa git commit e git push. Ele define como o time versiona, revisa, protege, integra, entrega, audita e recupera software em produção.

Resumo em uma frase

Git em nível sênior é disciplina de engenharia: histórico confiável, colaboração segura, automação, governança, auditoria e entrega de software com risco controlado.
