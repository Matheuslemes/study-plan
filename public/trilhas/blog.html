Criar uma plataforma pública e própria para publicar conteúdo técnico, demonstrar evolução profissional, registrar projetos e construir autoridade técnica com controle de SEO, dados e monetização.

Um produto real em produção, com código versionado, arquitetura documentada, conteúdo publicado, painel admin, analytics, newsletter e base para produtos digitais.

4. Monólito modular

Arquitetura

O projeto deve iniciar como monólito modular. Essa abordagem reduz custo operacional e complexidade, mas preserva separação por domínio e permite extração futura de serviços caso o produto cresça.

Quando reavaliar microserviços

  • Volume acima de 1 milhão de pageviews/mês e escala vertical antieconômica.
  • Módulo de pagamentos exigindo time dedicado e deploy próprio.
  • Dois módulos com ciclos de deploy independentes e conflitantes.
  • Tempo de build acima de 15 minutos.

Comunicação entre módulos

SituaçãoMecanismoExemplo
Operação síncrona no mesmo requestChamada via interface/portPostService consulta UserReadPort.
Efeito colateral assíncronoSpring ApplicationEventPostPublishedEvent dispara indexação e e-mail.
Comunicação que pode falharEvento + retryEnvio de e-mail e webhook externo.

Anti-Corruption Layer entre módulos

Módulos não devem expor entidades JPA uns aos outros. O consumo deve ocorrer por portas, DTOs ou eventos.

public interface PostReadPort {
    PostSummary findBySlug(String slug);
    List<PostSummary> findPublished(Pageable pageable);
}
// Analytics consome PostReadPort, mas nunca conhece a entidade JPA Post.

7. Autenticação, autorização e segurança

Security

A estratégia recomendada usa access token de curta duração, refresh token rotativo em cookie HttpOnly, detecção de reuso, roles e permissões por método.

Política de sessões

  • Permitir múltiplos dispositivos simultâneos.
  • Cada dispositivo possui refresh token próprio.
  • Logout revoga apenas a sessão atual.
  • Opção “sair de todos os dispositivos” revoga todos os tokens do usuário.
  • Reuso de refresh token revogado invalida a família de tokens do usuário.

Controles obrigatórios

8. Conteúdo, publicação e uploads

Conteúdo

O fluxo editorial deve permitir escrita técnica com Markdown/MDX, assets otimizados, publicação agendada e propagação de eventos para cache, busca, newsletter e SEO.

Validação de arquivos

  • Nunca confiar apenas na extensão do arquivo.
  • Validar magic bytes para JPEG, PNG, PDF e formatos permitidos.
  • Limitar tamanho, content type e dimensões.
  • Converter imagens para WebP/AVIF e servir via CDN.

Fluxos preservados do PDF

Fluxo de publicação:
Admin UI -> Posts API -> PostgreSQL -> PostPublishedEvent -> Redis -> FTS/pgvector -> Newsletter -> Sitemap/RSS/OG.

Fluxo de upload:
Admin Frontend seleciona arquivo -> Media API gera presigned-url -> Object Storage recebe PUT direto S3/R2/Azure -> PostgreSQL registra media_assets -> CDN/next-image serve WebP/AVIF.

11. Cache, busca e performance

Redis

Redis deve ser usado para reduzir carga do banco, controlar taxa, armazenar locks temporários e acelerar leituras públicas. PostgreSQL Full Text Search atende o MVP; Meilisearch/OpenSearch entram somente se as métricas justificarem.

Chaves e estratégias Redis

ChaveUsoTTL

blog:posts:detail:{slug}Detalhe do post30 a 60 min
blog:categories:* / blog:tags:*Categorias e tags1 a 6 h
rate-limit:{ip}:{endpoint}Rate limiting públicojanela móvel

Quando migrar busca para Meilisearch/OpenSearch

  • Mais de 500 artigos.
  • Reclamações de resultados irrelevantes.
  • Necessidade de facets por tag, categoria e data simultaneamente.
  • Necessidade de typo tolerance e ranking mais sofisticado.

Estratégia de deploy

  • Fluxo: feature branch -> Pull Request -> CI -> staging -> main -> produção.
  • Frontend: Vercel com preview deploys e production deploy.
  • Backend: Render, Railway, Fly.io, AWS, Azure ou VPS com Docker.
  • Banco: PostgreSQL gerenciado separado por ambiente.
  • Redis: serviço gerenciado em produção.
  • Migrations: expand-contract para zero downtime.
  • Rollback: redeploy do último container funcional e migration de compensação quando necessário.

Zero downtime

O novo container só deve receber tráfego depois de passar readiness/liveness. Migrations destrutivas nunca devem rodar junto com código antigo.

17. Priorização recomendada

Prioridade

MVP obrigatório

  • Auth com JWT e refresh token.
  • CRUD de posts, categorias e tags.
  • Admin básico.
  • SEO, sitemap, robots e RSS.
  • PostgreSQL, Flyway, Redis básico.
  • Swagger/OpenAPI e testes essenciais.
  • Deploy frontend/backend em staging e produção.

Depois do MVP

  • Comentários, favoritos e histórico.
  • Newsletter com campanhas.
  • Analytics interno.
  • Produtos digitais e checkout.
  • Área premium.
  • RAG, auto-tagging e agente do blog.
  • i18n, PWA e features avançadas.

Critério para parar de adicionar features

  • Se os últimos 5 posts não foram publicados, foque em conteúdo.
  • Se a newsletter não tem 100 assinantes, foque em SEO e distribuição.
  • Se existe bug crítico aberto há mais de 7 dias, corrija antes de evoluir escopo.
  • Se Lighthouse está abaixo de 90, fortaleça a base antes de adicionar complexidade.
