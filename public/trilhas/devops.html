Resumo executivo

Trilha DevOps integrada ao plano de estudos, ao portfólio e à operação real de software.

DevOps

A trilha DevOps deve transformar o projeto de blog em um produto operável: código versionado, containers, pipeline, deploy automatizado, infraestrutura como código, Kubernetes, observabilidade, segurança, runbooks, métricas de entrega e incident response.

O objetivo não é apenas “saber ferramentas”. O objetivo é demonstrar que você consegue colocar uma aplicação em produção, diagnosticar falhas, reduzir risco de deploy, medir estabilidade, proteger a supply chain e documentar decisões operacionais.

Regra central da trilha

Toda feature do blog deve passar por pipeline, staging, health check, observabilidade e documentação operacional. Nada de deploy manual em produção; toda exceção deve virar ADR com justificativa e prazo de correção.

Linux, Git e Networking

Base operacional que sustenta Docker, Kubernetes, cloud e troubleshooting.

Fundação

Linux operacional

Comandos, processos, logs, permissões, filesystem, systemd, cron, variáveis, shell scripting e análise de consumo.

Redes para DevOps

DNS, TCP/IP, HTTP/S, TLS, portas, firewall, NAT, CIDR, proxy reverso, load balancer e troubleshooting de conectividade.

Git profissional

Branches, PR, trunk-based, conventional commits, rebase, tags, releases, changelog, hooks e estratégia de versionamento.

Checklist técnico

  • Diagnosticar processo com ps, top, htop, pidstat e systemctl.
  • Ler logs com journalctl, tail, grep, awk e jq.
  • Diagnosticar rede com curl, dig, nslookup, ss, lsof, traceroute e tcpdump.
  • Explicar diferenças entre problema de DNS, firewall, rota, certificado, proxy e aplicação.
  • Criar scripts idempotentes de setup, build, backup e validação de ambiente.
  • Aplicar Git Flow simplificado ou trunk-based com PR, CI obrigatório e release tags.

Entregáveis

  • runbooks/linux-troubleshooting.md: CPU alta, memória alta, disco cheio, porta ocupada, serviço não sobe.
  • runbooks/network-troubleshooting.md: DNS, TLS, timeout, connection refused, 502, 504 e CORS.
  • scripts/healthcheck.sh: valida API, banco, Redis, disco, memória e portas.
  • CONTRIBUTING.md: padrão de branch, commit, PR, revisão e release.

Docker e Containerização

Ambiente reproduzível, imagens otimizadas e base para deploy moderno.

Containers

Conteúdo obrigatório

  • Images, containers, layers, build context, cache, tags, registry e digest.
  • Dockerfile multi-stage para Java/Spring e Next.js.
  • Docker Compose com Postgres, Redis, Kafka/localstack quando necessário.
  • Networks: bridge, host, DNS interno e comunicação entre serviços.
  • Volumes: bind mount, named volume, backup e persistência.
  • Health checks, env vars, secrets locais, logs e restart policies.
  • Segurança: non-root, distroless/slim, readonly filesystem, scan e menor privilégio.

Padrão esperado de imagem

# Exemplo conceitual: Spring Boot multi-stage
FROM eclipse-temurin:21-jdk AS build
WORKDIR /app
COPY mvnw pom.xml ./
COPY .mvn .mvn
RUN ./mvnw -q -DskipTests dependency:go-offline
COPY src src
RUN ./mvnw -q clean package -DskipTests

FROM eclipse-temurin:21-jre
WORKDIR /app
RUN useradd -r -u 1001 appuser
COPY --from=build /app/target/*.jar app.jar
USER appuser
EXPOSE 8080
HEALTHCHECK --interval=30s --timeout=3s \
  CMD curl -f http://localhost:8080/actuator/health || exit 1
ENTRYPOINT ["java","-jar","app.jar"]

Entregáveis

  • Dockerfile de produção para API Java e frontend.
  • docker-compose.yml com Postgres, Redis, API, frontend e observabilidade local.
  • Scan de imagem com Trivy no pipeline.
  • README com comandos de build, run, logs, shell, volumes e troubleshooting.

CI/CD, Qualidade e DORA Metrics

Entrega automatizada com segurança, rastreabilidade e medição de performance.

Entrega

Pipeline mínimo profissional

  • Trigger em Pull Request e merge na branch principal.
  • Build frontend/backend.
  • Testes unitários, integração e lint.
  • JaCoCo/Istanbul e quality gate.
  • SonarQube, CodeQL, Dependabot e Trivy.
  • Build e push de imagem com tag semântica e SHA.
  • Deploy em staging, smoke test e promoção controlada para produção.
  • Rollback documentado e, quando possível, automatizado.

DORA Metrics obrigatórias

  • Deployment frequency: frequência de deploy.
  • Change lead time: tempo do commit até produção.
  • Change failure rate: percentual de mudanças que causam falha.
  • Failed deployment recovery time / MTTR: tempo para recuperar falha.
  • Reliability: cumprimento de SLOs e estabilidade percebida.

Exemplo de workflow GitHub Actions

name: ci-cd

on:
  pull_request:
  push:
    branches: [main]

jobs:
  backend:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-java@v4
        with:
          distribution: temurin
          java-version: '21'
          cache: maven
      - name: Test
        run: ./mvnw clean verify
      - name: Build image
        run: docker build -t ghcr.io/org/blog-api:${{ github.sha }} .
      - name: Security scan
        run: trivy image --exit-code 1 --severity HIGH,CRITICAL ghcr.io/org/blog-api:${{ github.sha }}

  deploy-staging:
    needs: backend
    runs-on: ubuntu-latest
    environment: staging
    steps:
      - name: Deploy
        run: echo "helm upgrade --install blog-api ./chart --set image.tag=${{ github.sha }}"
      - name: Smoke test
        run: curl -f https://staging.example.com/health

Entregáveis

  • .github/workflows/ci.yml: build, testes, lint, coverage, Sonar, CodeQL e Trivy.
  • .github/workflows/deploy.yml: deploy staging/prod, smoke test e rollback manual controlado.
  • docs/dora-metrics.md: métricas mensais do projeto.
  • CHANGELOG.md e estratégia de release tags.

SRE, Incident Response e Disaster Recovery

Confiabilidade mensurável e resposta operacional madura.

SRE

SLIs e SLOs do blog

  • Disponibilidade: API pública responde 99.5%+ no MVP.
  • Latência: p95 de leitura cacheada abaixo de 300 ms.
  • Erro: taxa 5xx abaixo de 1%.
  • Deploy: rollback disponível em até 15 minutos.
  • Recuperação: RPO máximo de 24h e RTO máximo de 2h no MVP.

Incident response

  • Classificar severidade: SEV1, SEV2, SEV3.
  • Acionar runbook correto.
  • Registrar início, impacto, diagnóstico, ação e encerramento.
  • Fazer postmortem sem culpabilização.
  • Criar follow-ups e prevenir recorrência.

Cenários obrigatórios de simulação

  • API fora do ar após deploy ruim.
  • Banco lento por query sem índice.
  • Redis indisponível e API degradando para banco.
  • Fila acumulada por worker parado.
  • Ingress retornando 502.
  • Custo anormal por logs excessivos ou NAT Gateway.
  • Restore de backup do banco em ambiente separado.

Artefatos

  • runbooks/api-down.md, db-slow.md, redis-down.md, queue-backlog.md.
  • postmortems/AAAA-MM-DD-incidente-simulado.md.
  • docs/slo-error-budget.md.
  • docs/disaster-recovery.md.

Roadmap DevOps integrado às 8 fases

Cronograma coeso com o plano anterior de 64 semanas.

64 semanas

Fase 1 — Fundamentos operacionais

Sem 1–8

Foco: Linux, Git, shell, processos, filesystem, SSH e networking inicial.

  • Terminal, permissões, systemd, journalctl, cron e logs.
  • TCP/IP, DNS, HTTP/S, TLS, portas e firewall básico.
  • Git: branching, PR, merge, rebase, tags e commits convencionais.
  • Runbooks iniciais de Linux e rede.

Fase 2 — Docker e ambiente local

Sem 9–16

Foco: containers, Dockerfile, Compose, registry e segurança básica.

  • Docker multi-stage para Java/Next.js.
  • Compose com Postgres, Redis e API.
  • Networks, volumes, health checks e logs.
  • Scan de imagens e hardening inicial.

Fase 3 — CI/CD e qualidade automatizada

Sem 17–24

Foco: GitHub Actions/Jenkins, quality gates, security scans e deploy inicial.

  • Pipeline build → test → lint → coverage → Sonar → Trivy.
  • Artifacts, cache, matrix, secrets e reusable workflows.
  • Staging automático e smoke tests.
  • DORA Metrics registradas desde o primeiro deploy.

Fase 4 — Kubernetes operacional

Sem 25–32

Foco: Kubernetes, probes, ingress, config, secrets e troubleshooting.

  • Pods, deployments, services, ingress, configmaps, secrets e resources.
  • Liveness, readiness e startup probes com Actuator.
  • Rolling update, blue/green, canary e rollback.
  • Laboratórios de CrashLoopBackOff, ImagePullBackOff, OOMKilled e ingress 502.

Fase 5 — Terraform, observabilidade e cloud

Sem 33–40

Foco: IaC, Helm, autoscaling, Prometheus, Grafana e OpenTelemetry.

  • Terraform: modules, state, backend, workspaces e environments.
  • Helm charts e values por ambiente.
  • Prometheus + Grafana + Alertmanager.
  • OpenTelemetry, Jaeger, logs e correlation IDs.

Fase 6 — SRE, DevSecOps e chaos

Sem 41–48

Foco: SLO, error budget, incident response, IaC testing e segurança.

  • Terratest, Checkov, tfsec e policy-as-code.
  • DevSecOps: CodeQL, Trivy, Gitleaks, SBOM e ZAP.
  • SLO-based alerting, golden signals e postmortem.
  • Chaos engineering: game days e blast radius controlado.

Fase 7 — GitOps, produção e platform

Sem 49–56

Foco: ArgoCD, produção Kubernetes, logging, APM, security e platform engineering.

  • GitOps com ArgoCD, sync policies, auto-sync e rollback.
  • K8s production: PDB, topology spread, affinity e NetworkPolicies.
  • EFK/Loki, Elastic APM/Datadog e infrastructure monitoring.
  • Golden paths, self-service, templates e DX.

Fase 8 — Portfólio DevOps final

Sem 57–64

Foco: auditoria final, DR, runbooks, FinOps, performance e apresentação técnica.

  • Infrastructure review completo.
  • DR drill com backup, restore, RTO/RPO e relatório.
  • Load testing final, capacity planning e FinOps report.
  • Case study: do commit ao deploy com incidente simulado e postmortem.

Checklist de execução

Regras práticas para garantir que o estudo gere portfólio real.

Execução

Checklist semanal

  • Estudar DevOps 1,5h/dia no bloco 14:00–15:30.
  • Aplicar pelo menos 1 melhoria operacional no blog.
  • Registrar 1 erro ou incidente simulado em runbook.
  • Fazer 1 deploy via pipeline, mesmo que em staging/local.
  • Atualizar dashboard, alerta ou métrica operacional.

  • Pipeline está mais rápido ou mais seguro que no mês anterior?
  • Há rollback testado?
  • Há observabilidade suficiente para diagnosticar erro 5xx?
  • Há scan de segurança antes do deploy?
  • Há documentação atualizada de deploy e incidentes?
  • DORA Metrics foram medidas e comparadas?

Projeto central: Blog Portfólio Operável

O próprio blog deve ser a vitrine DevOps. A melhor prova de competência é mostrar o caminho completo: commit → CI → build → scan → registry → deploy → health check → observabilidade → alerta → incidente simulado → postmortem.

Critério de “pronto para entrevista pleno”

  • Explicar um pipeline de ponta a ponta sem consultar anotações.
  • Mostrar um deploy real com rollback.
  • Demonstrar troubleshooting de Kubernetes com comandos reais.
  • Mostrar Terraform com módulos, ambientes e remote state.
  • Mostrar dashboard com métricas de API, banco, Redis, Kubernetes e produto.
  • Apresentar um postmortem simulado com causa raiz e ação preventiva.
  • Apresentar relatório de custo e estratégia de otimização.
