Java 21 e fundamentos modernos

Base da linguagem para escrever código expressivo, seguro e performático.

Java Core

Conceitos obrigatórios

  • Tipos primitivos, wrappers, autoboxing, comparação por valor/referência e imutabilidade.
  • OOP: encapsulamento, coesão, acoplamento, herança, composição, polimorfismo e interfaces.
  • Generics: type parameters, bounded types, wildcards, variance e type erasure.
  • Collections: List, Set, Map, Queue, equals/hashCode, ordenação, hashing e complexidade.
  • Streams: map/filter/reduce, collectors, parallel stream com cautela e legibilidade.
  • Records para DTOs/value carriers; sealed classes para hierarquias controladas.
  • Virtual Threads para concorrência de alta escala em workloads bloqueantes, sem confundir com ganho mágico de CPU.
  • Exceptions: checked/unchecked, tradução de exceções, contratos de erro e logging correto.

Armadilhas comuns

  • Usar herança onde composição resolveria melhor.
  • Criar DTO mutável sem necessidade.
  • Ignorar equals/hashCode em entidades e value objects.
  • Usar Stream em excesso quando um loop é mais claro.
  • Tratar Optional como campo de entidade ou parâmetro generalizado.
  • Engolir exceção ou logar sem contexto.
  • Confundir Virtual Threads com solução para banco lento, locks ou gargalos externos.

Exemplo: sealed class para resultado de caso de uso

public sealed interface CreatePostResult permits CreatePostResult.Success, CreatePostResult.DuplicatedSlug, CreatePostResult.InvalidAuthor {

    record Success(UUID postId, String slug) implements CreatePostResult {}
    record DuplicatedSlug(String slug) implements CreatePostResult {}
    record InvalidAuthor(UUID authorId) implements CreatePostResult {}
}

public ResponseEntity<?> handle(CreatePostResult result) {
    return switch (result) {
        case CreatePostResult.Success s -> ResponseEntity.status(201).body(s);
        case CreatePostResult.DuplicatedSlug e -> ResponseEntity.status(409).body(e);
        case CreatePostResult.InvalidAuthor e -> ResponseEntity.status(422).body(e);
    };
}

Critério de domínio

Você domina Java Core quando consegue explicar por que escolheu uma estrutura de dados, como equals/hashCode afetam collections, quando usar record/sealed class e como concorrência impacta latência, throughput e consumo de recursos.

Persistência, JPA/Hibernate e bancos

O diferencial real de um backend Java sênior está em dados, transações e performance.

Dados

JPA/Hibernate avançado

  • Ciclo de vida da entidade: transient, managed, detached e removed.
  • Dirty checking, flush, persistence context e impacto em performance.
  • Lazy vs eager loading, N+1, fetch join e EntityGraph.
  • Projections, DTO queries, paginação e batch fetching.
  • Optimistic locking com @Version e pessimistic locking quando necessário.
  • Transações: propagation, isolation, rollback rules e boundaries.
  • HikariCP: pool size, timeout, leak detection e saturação.

Banco de dados em produção

  • PostgreSQL: índices B-tree, compostos, parciais, GIN e análise de plano.
  • EXPLAIN ANALYZE para provar gargalo e validar correção.
  • Flyway com migrations versionadas, reversibilidade e expand-contract.
  • MongoDB para documentos com modelagem orientada ao acesso.
  • Redis para cache, locks, rate limiting, idempotência e TTL.
  • Consistência entre serviços e riscos de dual-write.
  • Backup, restore, retenção e validação de recuperação.

@Entity
@Table(name = "posts", indexes = {
    @Index(name = "idx_posts_slug", columnList = "slug", unique = true),
    @Index(name = "idx_posts_status_published", columnList = "status,published_at")
})
public class PostEntity {

    @Id
    private UUID id;

    @Column(nullable = false, length = 180)
    private String title;

    @Column(nullable = false, unique = true, length = 200)
    private String slug;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 30)
    private PostStatus status;

    @Version
    private long version;

    @Column(name = "created_at", nullable = false)
    private Instant createdAt;

    @Column(name = "updated_at", nullable = false)
    private Instant updatedAt;
}

Checklist de tuning JPA

  • Medir antes de otimizar.
  • Ativar logs SQL apenas em ambiente controlado.
  • Identificar N+1 com teste de integração e query counter.
  • Validar plano com EXPLAIN ANALYZE.
  • Revisar índice de acordo com filtros, ordenação e cardinalidade.
  • Ajustar pool HikariCP com base em banco, CPU e latência.
  • Evitar transação longa envolvendo chamada externa.

API Design profissional

Contratos HTTP claros, evolutivos, seguros e previsíveis.

REST

Princípios

  • URLs orientadas a recursos e não a ações internas.
  • Status codes coerentes: 200, 201, 202, 204, 400, 401, 403, 404, 409, 422, 429, 500.
  • Erros com RFC 7807 / Problem Details.
  • Idempotência em operações sensíveis como pagamento, webhook, like e criação externa.
  • Paginação por cursor para feeds grandes.
  • Versionamento explícito e política de depreciação.
  • Rate limit, timeout, retry e circuit breaker definidos.

Contratos

  • OpenAPI atualizado no pipeline.
  • DTOs separados por request/response.
  • Backward compatibility como regra.
  • Consumer-driven contract tests quando houver múltiplos consumidores.
  • Headers de correlação: X-Request-Id / traceparent.
  • Campos de data em ISO-8601 e timezone claro.
  • Validação com mensagens consistentes.

  • DTO não vaza entidade?

Quality gate mínimo

  • Build sem warning crítico.
  • Testes unitários e integração passando.
  • Contrato consumidor/provedor validado no pipeline antes de publicar versão incompatível.
  • Mutation score acompanhado nas regras críticas; mutante sobrevivente exige análise da assertion.
  • Cobertura nova mínima de 70% e módulos críticos acima de 85%.
  • Sonar sem bug/blocker/critical.
  • Sem segredo em repositório.
  • OpenAPI atualizado.
  • Docker image escaneada quando aplicável.

Arquitetura de software aplicada

O ponto que diferencia execução competente de engenharia sênior.

Architecture

Monólito modular primeiro

Para o blog/portfólio, comece com monólito modular: menor custo operacional, deploy simples, fronteiras por domínio e extração futura se houver necessidade real.

Microsserviços com critério

Extraia serviço apenas se houver escala, times independentes, deploy conflitante, isolamento de falha, custo de escala vertical alto ou requisitos claros de autonomia.

Quando usar cada padrão

Padrão Uso adequado Risco se mal usado
DDD Domínio com regra rica, invariantes e linguagem de negócio. Overengineering para CRUD simples.
Hexagonal Domínio precisa ficar isolado de banco, HTTP, fila e ferramentas. Excesso de interfaces sem ganho real.
CQRS Leitura e escrita têm modelos, escala ou requisitos diferentes. Duplicação e complexidade desnecessária.
Outbox Precisa salvar no banco e publicar evento de forma confiável. Scheduler/consumer mal monitorado vira fila invisível.
Saga Processo distribuído com compensações entre serviços. Dificuldade de depuração e consistência.
Event Sourcing Auditoria completa e reconstrução de estado são requisitos fortes. Complexidade alta para domínio simples.

Mensageria, Kafka e eventos

Essencial para microsserviços, integração assíncrona e sistemas distribuídos.

Events

Kafka profissional

  • Topics, partitions, replication factor e retenção.
  • Consumer groups, offsets, commits e rebalances.
  • Ordering por chave e impacto no particionamento.
  • At-least-once vs exactly-once e idempotent consumer.
  • Schema evolution, versionamento de eventos e compatibilidade.
  • DLQ, retry topics, poison messages e backoff.
  • Lag monitoring, throughput e tuning de consumers.

Padrões de evento

  • Transactional Outbox para evitar dual-write.
  • Inbox/idempotency table para processar evento uma vez logicamente.
  • Event notification vs event-carried state transfer.
  • Saga coreografada vs orquestrada.
  • Contrato de evento com versionamento sem quebrar consumidor.
  • Tracing assíncrono preservando correlation ID.
  • Runbook para fila acumulada e consumer parado.

Concorrência e paralelismo em Java

Lacuna identificada no diagnóstico: o tema aparecia disperso, sem seção própria. É assunto recorrente em entrevista sênior e causa raiz frequente de incidente em produção.

Concorrência

Fundamentos e modelo de memória

  • Thread e Runnable: ciclo de vida, estados e por que criar thread manualmente quase nunca é a resposta.
  • Java Memory Model: visibilidade, reordenação, happens-before e o que volatile garante — e o que não garante.
  • Race condition × deadlock × livelock × starvation: reconhecer cada um pelo sintoma.
  • Imutabilidade como estratégia primária: o objeto que não muda não precisa de sincronização.

synchronized, locks e atômicos

  • synchronized: bloco × método, monitor object e granularidade do lock.
  • ReentrantLock: tryLock com timeout, fairness e por que ele resolve o que synchronized não resolve.
  • ReadWriteLock e StampedLock para carga predominante de leitura.
  • AtomicInteger, AtomicReference, CAS e LongAdder sob alta contenção.
  • Coleções concorrentes: ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue.

Thread pools e ExecutorService

  • ExecutorService, ThreadPoolExecutor e o significado real de core size, max size e queue.
  • Dimensionamento: pool para tarefa CPU-bound × IO-bound e por que copiar número mágico da internet gera saturação.
  • RejectedExecutionHandler: o que acontece quando a fila enche — e por que fila ilimitada é uma armadilha.
  • ScheduledExecutorService e shutdown correto (shutdown × shutdownNow × awaitTermination).
  • Thread pool em Spring: @Async, TaskExecutor e o pool do servidor web como recurso finito.

CompletableFuture e composição assíncrona

  • supplyAsync, thenApply, thenCompose e thenCombine: encadear sem bloquear.
  • allOf e anyOf para paralelizar chamadas independentes a serviços externos.
  • Tratamento de falha: exceptionally, handle, whenComplete e timeout com orTimeout.
  • A armadilha do join()/get() prematuro, que transforma código assíncrono em bloqueante.
  • Executor explícito: nunca deixar tarefa de IO no ForkJoinPool.commonPool por engano.

Virtual Threads (Java 21)

  • Platform thread × virtual thread: custo de criação, escalonamento e por que "uma thread por requisição" volta a ser viável.
  • Executors.newVirtualThreadPerTaskExecutor() e integração com Spring Boot 3.2+.
  • Pinning: quando synchronized prende a virtual thread ao carrier e como diagnosticar.
  • Structured Concurrency (preview): StructuredTaskScope para tarefas com ciclo de vida comum.
  • Quando NÃO usar Virtual Threads: tarefas CPU-bound continuam limitadas pelos núcleos e pedem paralelismo limitado, não mais concorrência.
  • Não use para mascarar banco lento, pool de conexões saturado ou API externa sem capacidade: a dependência escassa continua impondo o limite.
  • Evite adotar antes de diagnosticar pinning em bibliotecas com synchronized, código nativo ou seções críticas longas.
  • Prefira fila limitada e backpressure quando o sistema precisa rejeitar ou regular carga; uma virtual thread por tarefa não substitui controle de admissão.
  • Não espere redução automática de latência: virtual threads aumentam capacidade para espera bloqueante, mas não tornam uma operação individual mais rápida.

Prática e critério de domínio

  • Reproduzir uma race condition de propósito, observar o defeito e corrigi-lo de três formas diferentes.
  • Provocar um deadlock, capturar o thread dump e identificar o ciclo de espera.
  • Paralelizar três chamadas externas com CompletableFuture e medir o ganho real de latência.
  • Comparar o mesmo endpoint com platform threads e virtual threads sob carga.
  • Critério: explicar em voz alta por que uma solução é thread-safe, sem consultar.

Onde entra no plano: fundamentos e thread pools na Fase 2 (Java avançado); CompletableFuture aplicado a integrações na Fase 5 (performance); virtual threads e diagnóstico de contenção na Fase 6 (observabilidade e troubleshooting).

Performance, JVM e troubleshooting

Como investigar problemas reais além de “funciona na minha máquina”.

Performance

Ferramentas e técnicas

  • Thread dump para deadlock, contenção e saturação.
  • Heap dump para memory leak e retenção indevida.
  • GC logs para pausas, throughput e pressão de memória.
  • Java Flight Recorder e profiler para hotspots.
  • k6/Gatling para carga e regressão de performance.
  • APM para flame graph, spans lentos e dependências externas.
  • EXPLAIN ANALYZE para queries e índices.

Problemas comuns

  • N+1 em listagem paginada.
  • Pool de conexão saturado.
  • Timeout inexistente em chamada externa.
  • Retry sem backoff causando tempestade.
  • Cache stampede em endpoint quente.
  • Transação longa segurando lock.
  • Serialização JSON pesada ou payload excessivo.

Fluxo de diagnóstico

1. ReproduzirDefina entrada, ambiente, volume e métrica afetada.
2. MedirLogs, traces, métricas, query plan, thread/heap dump quando necessário.
3. HipóteseFormule causa provável e valide com evidência.
4. CorrigirFaça mudança pequena e mensurável.
5. ProvarCompare antes/depois com métricas e teste de regressão.
6. DocumentarRegistre causa, correção, impacto e prevenção.

Legado, migração e manutenção evolutiva

Mercado real envolve sistemas existentes, não só projetos novos.

Legacy

Migrações críticas

  • Java 8/11 → 17/21: dependências, build, bytecode, APIs removidas e testes.
  • Spring Boot 2 → 3: Java 17 mínimo, Spring 6 e namespace jakarta.*.
  • javax.* → jakarta.*: imports, libs compatíveis, validação e JPA.
  • JUnit 4 → JUnit 5: extension model e modernização de testes.
  • RestTemplate → WebClient/HTTP interfaces quando fizer sentido.

Refatoração segura

  • Adicionar testes antes de mudar comportamento.
  • Quebrar classe gigante por caso de uso.
  • Extrair portas/adapters gradualmente.
  • Preservar contrato público.
  • Usar feature flags em mudanças arriscadas.
  • Registrar ADR para decisões importantes.

Checklist de sistema legado

  • Existe teste cobrindo comportamento atual?
  • Qual contrato externo não pode quebrar?
  • Há dependência abandonada ou vulnerável?
  • O build é reproduzível?
  • Existem logs suficientes para diagnosticar?
  • O banco tem migrations confiáveis?
  • A mudança pode ser feita em etapas?

Consulta rápida

Resumo objetivo para revisão antes de codar, revisar PR ou entrevista.

Quick Reference
Tópico O que lembrar Pergunta de entrevista
Java Collections dependem de equals/hashCode; generics sofrem type erasure; records são imutáveis por contrato superficial. Quando usar record, class ou sealed class?
Spring Controller não deve carregar regra; service orquestra; domain protege invariantes. Como você estrutura uma API Spring Boot grande?
JPA N+1, lazy loading, transação longa e índice errado são gargalos frequentes. Como diagnosticar query lenta?
Security Autenticação prova identidade; autorização define acesso; claims precisam ser confiáveis. Como proteger endpoint admin?
API Contrato deve ser estável, versionado, validado e documentado. Como evoluir API sem quebrar cliente?
Kafka Partição define paralelismo e ordering; consumer precisa ser idempotente. Como evitar processar evento duplicado?
Cache Cache melhora leitura, mas introduz invalidação e consistência. Quando usar cache-aside?
Resiliência Timeout sempre; retry com backoff; circuit breaker para falha persistente. Quando retry piora o sistema?
Observabilidade Log diz o que aconteceu; métrica mostra tendência; trace mostra caminho. Como investigar p95 alto?
Arquitetura Todo padrão tem custo. Justifique por problema real, não por moda. Quando não usar microsserviços?
