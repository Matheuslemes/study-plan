Critério de evolução

Não avance apenas por “ter visto” o tópico. Avance quando conseguir aplicar, explicar trade-offs, testar, documentar e defender a decisão em code review.

Fundamentos da Web

A base obrigatória antes de React, Next.js ou qualquer framework.

Web Platform

Antes de frameworks, domine como a plataforma funciona: browser, HTTP/HTTPS, DNS básico, URL, request/response, HTML, CSS, JavaScript, DOM, CSSOM, eventos, renderização, acessibilidade, segurança e performance.

URL → respostaEntenda DNS, TLS, request, headers, cookies, cache HTTP, CDN e status codes.
Parsing e renderizaçãoHTML gera DOM; CSS gera CSSOM; o navegador calcula estilo, layout, paint e composição.
JavaScript no browserJS pode bloquear parsing, manipular DOM, responder eventos, fazer requests e consumir Web APIs.
SSR, CSR, SSG e streamingCada modelo muda tempo de resposta, SEO, hidratação, cache, custo de servidor e experiência percebida.
O que um sênior explica Por que importa
O que acontece quando o usuário acessa uma URL. Base para diagnosticar falhas de rede, cache, DNS, autenticação e performance inicial.
Como HTML, CSS, JS, imagens e fontes são baixados. Ajuda a reduzir waterfall, bloquear menos o main thread e otimizar LCP/FCP.
Como cookies, CORS e headers impactam segurança. Evita vazamento de token, problemas de sessão, falhas de autorização e exposição indevida.
Como cache HTTP influencia performance. Permite projetar asset caching, revalidação, CDN e estratégia de deploy sem stale data perigoso.

HTML — do básico ao sênior

HTML como contrato semântico, acessível, performático e indexável.

Semântica

Básico

estrutura
  • <!DOCTYPE html>, <html>, <head>, <body>, <title> e meta tags.
  • Headings, parágrafos, links, imagens, listas, tabelas, formulários, inputs e buttons.
  • Entender o papel de cada elemento antes de estilizar ou componentizar.

Intermediário

semântica
  • <header>, <nav>, <main>, <section>, <article>, <aside> e <footer>.
  • <figure>, <figcaption>, <time>, <address>, <details>, <summary> e <dialog>.
  • Formulários acessíveis com label, fieldset, legend, required, autocomplete, inputmode e aria-describedby.

Avançado

SEO e performance
  • SEO técnico, Open Graph, Twitter Cards, robots, canonical URL, structured data e JSON-LD.
  • Imagens responsivas com loading, srcset, sizes, dimensões estáveis e formatos modernos.
  • Resource hints: preload, prefetch e preconnect com critério.

Sênior

contrato semântico
  • Preservar semântica dentro de frameworks, componentes e design systems.
  • Garantir navegação por teclado, landmarks e ordem lógica do documento.
  • Criar HTML que funcione de forma aceitável antes do JavaScript carregar.

Critérios de domínio

  • Revisar uma página e identificar problemas semânticos.
  • Substituir div e span desnecessários por elementos corretos.
  • Explicar quando usar button e quando usar a.
  • Criar formulários usáveis por teclado e leitores de tela.
<main>
  <section aria-labelledby="hero-title">
    <h1 id="hero-title">Produto financeiro para pequenas empresas</h1>
    <p>Compare planos, veja taxas e simule o custo total.</p>
    <a href="#simulador">Simular agora</a>
  </section>

  <form id="simulador" aria-describedby="simulador-help">
    <p id="simulador-help">Informe dados reais para uma simulação mais próxima.</p>
    <label for="valor">Valor desejado</label>
    <input id="valor" name="valor" inputmode="decimal" autocomplete="off" required />
    <button type="submit">Calcular</button>
  </form>
</main>

CSS — do básico ao sênior

De box model a arquitetura CSS escalável com tokens, temas e responsividade real.

Layout
Nível O que estudar Domínio esperado
Básico Seletores, propriedades, valores, classes, IDs, box model, margin, padding, border, width, height, display, position, cores, fontes, backgrounds, pseudo-classes e pseudo-elements. Entender como cada elemento ocupa espaço, como é pintado e como estilos entram em conflito.
Intermediário Flexbox, Grid, positioning, responsividade, media queries, mobile-first, fluid typography, CSS variables, transitions, animations, transform, z-index, stacking context, overflow, object-fit e aspect-ratio. Criar layouts responsivos sem hacks, resolver overflow e organizar spacing/tipografia.
Avançado Cascade, specificity, inheritance, cascade layers, container queries, logical properties, nesting, CSS Modules, design tokens, theme system, dark mode, reduced motion, clamp, subgrid e estratégias CSS. Reduzir conflitos de especificidade, criar componentes adaptáveis ao container e padronizar design system.
Sênior Arquitetura CSS escalável, tokens, temas, variants, CSS performático, integração com Figma/tokens, contraste, foco, erro, motion responsável, CSS para SSR, critical CSS e redução de layout shift. Escolher entre Tailwind, CSS Modules, Sass, CSS-in-JS e vanilla CSS por contexto técnico e organizacional.

Evite cascata acidental

Use escopo, layers, convenções e tokens. Baixa especificidade é mais sustentável que seletores longos.

Projete para componentes

Container queries, variants e tokens ajudam o componente a funcionar fora do layout original.

Responsividade real

Combine Grid/Flexbox, clamp(), unidades modernas, imagens fluidas e breakpoints mínimos.

:root {
  --color-bg: #07090f;
  --color-surface: #111827;
  --color-primary: #38bdf8;
  --space-2: .5rem;
  --space-4: 1rem;
  --radius-md: .75rem;
}

.card {
  background: var(--color-surface);
  border-radius: var(--radius-md);
  padding: clamp(var(--space-2), 2vw, var(--space-4));
}

@container (min-width: 42rem) {
  .card { display: grid; grid-template-columns: 1fr auto; }
}

JavaScript — do básico ao sênior

Linguagem, runtime, Web APIs, assincronismo e performance no navegador.

Runtime

Básico

sintaxe + DOM
  • Variáveis, tipos primitivos, objetos, arrays, operadores, condicionais, loops e funções.
  • Escopo, hoisting, closures básicos, DOM, eventos, classes, atributos e Fetch básico.
  • Manipular a interface sem depender de framework.

Intermediário

ES moderno
  • ES Modules, destructuring, spread/rest, template literals, arrow functions e array methods.
  • Map, Set, WeakMap, WeakSet, Date, Intl, JSON, Promises, async/await e error handling.
  • Fetch API, AbortController, storage, cookies e event delegation.

Avançado

runtime
  • Execution context, call stack, heap, event loop, task queue, microtask queue e Promises internals.
  • Prototypes, this, classes, composition, modules, tree shaking e memory leaks.
  • Debounce, throttle, generators, iterators, Proxy, Reflect, Web Workers, Service Workers e observers.

Sênior

debugging
  • Assincronismo e concorrência no browser, cancelamento de requests, race conditions e Web Workers.
  • Service Workers para PWA/offline/cache, otimização de bundle e uso correto de APIs nativas.
  • Debugging avançado no DevTools, profiling de CPU/memória e estratégia de erro no client.

Critérios de domínio

  • Explicar event loop com microtasks e macrotasks.
  • Identificar vazamento de memória.
  • Cancelar request quando componente desmonta.
  • Mover processamento pesado para Web Worker.
  • Reduzir JavaScript enviado ao browser e escrever código resiliente a falhas de rede.
const controller = new AbortController();

async function searchProducts(query) {
  const response = await fetch(`/api/products?q=${encodeURIComponent(query)}`, {
    signal: controller.signal,
  });

  if (!response.ok) {
    throw new Error(`Falha HTTP: ${response.status}`);
  }

  return response.json();
}

// Ao sair da tela, cancelar request pendente para evitar race condition.
controller.abort();

TypeScript — do básico ao sênior

Tipagem como ferramenta de arquitetura, modelagem de domínio e prevenção de estados inválidos.

Type Safety
Nível Conteúdos Evidência prática
Básico Tipos primitivos, arrays, objects, functions, type aliases, interfaces, optional properties, union types, literal types, inference e annotations. Criar componentes, DTOs e serviços sem recorrer a any.
Intermediário Generics, narrowing, discriminated unions, intersections, utility types, type guards, assertion functions, unknown vs any e never. Modelar fluxos de UI com estados explícitos e reduzir bugs de null/undefined.
Avançado Conditional types, mapped types, template literal types, recursive types, branded types, satisfies, const assertions, module augmentation, declaration files, Zod + TS e runtime validation. Criar clients de API, rotas, formulários e SDKs tipados.
Sênior TypeScript como arquitetura, domínio com tipos, contratos de API, design systems tipados, estados impossíveis, tsconfig rigoroso e equilíbrio entre segurança e legibilidade. Revisar PRs considerando legibilidade, risco, complexidade de tipos e segurança de contrato. 
type RemoteData<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }
  | { status: "error"; error: string };

function renderUsers(state: RemoteData<User[]>) {
  switch (state.status) {
    case "idle": return "Aguardando busca";
    case "loading": return "Carregando";
    case "success": return state.data.map(user => user.name).join(", ");
    case "error": return state.error;
  }
}

Regra sênior

Tipos devem guiar o uso correto da aplicação. Quando tipos viram quebra-cabeça ilegível, a abstração precisa ser simplificada.

React — do básico ao sênior

Componentização, hooks, renderização, arquitetura de estado e component API design.

React

Básico

componentes
  • JSX, components, props, state, events, conditional rendering, lists, keys, forms, controlled components e composition.
  • Criar componentes pequenos, previsíveis e com responsabilidade clara.

Intermediário

hooks
  • useState, useEffect, useMemo, useCallback, useRef, useReducer, Context API e custom hooks.
  • Error boundaries, React Router, form libraries, data fetching e state management.
  • Separar lógica reutilizável em hooks sem esconder regra de negócio crítica.

Avançado

render cycle
  • Render cycle, reconciliation, component identity, keys avançado, controlled vs uncontrolled e derived state.
  • Composition patterns, compound components, render props, Context performance, Suspense, lazy loading, concurrent rendering, Server Components, hydration e streaming.
  • React Profiler, memoization criteriosa, state machines e headless components.

Sênior

arquitetura
  • Separar UI, composição e lógica de domínio.
  • Definir estratégia de estado local, global, server state e URL state.
  • Projetar component APIs acessíveis, testáveis, performáticas e sem acoplamento excessivo.
  • Lidar com SSR/hydration bugs, Suspense boundaries, Error boundaries, code splitting, bundle analysis e forms em escala.

Quando usar cada estado

Local: interação isolada. URL: filtros, paginação e busca compartilhável. Server state: dados remotos com cache/revalidação. Global: estado transversal real, não qualquer dado conveniente.

Next.js — do básico ao sênior

App Router, Server Components, cache, renderização, segurança, SEO e deploy.

Next.js
Tema O que dominar Erro comum
App Router Páginas, layouts, rotas, links, metadata, Server Components, Client Components, static assets, CSS Modules e deploy. Transformar tudo em Client Component por hábito.
Data fetching SSR, SSG, ISR, dynamic routes, route handlers, middleware, loading UI, error UI, not-found, cookies, headers e redirects. Fazer waterfall de dados e perder cache sem perceber.
Renderização avançada Streaming, Suspense, cache, revalidation, Server Actions, Edge runtime, image/font optimization, i18n e auth em SSR. Misturar segredo no client bundle ou depender só de proteção visual de rota.
Sênior Escolher SSR/SSG/ISR/CSR, desenhar cache server/client, revalidar por tempo/evento, usar cookies seguros, separar frontend/BFF/backend e medir Core Web Vitals. Escolher renderização por moda, sem requisito de produto, SEO, segurança, custo e cache.
SSRConteúdo dinâmico por request, bom para dados personalizados e SEO com atualização frequente.
SSGGeração estática, excelente para conteúdo estável, performance e cache agressivo.
ISRRegeneração incremental, bom equilíbrio para páginas com atualização periódica.
CSRInteração rica no client, mas deve ser usado com cuidado por custo de JS e SEO.

Outros frameworks e quando usar

Decisão técnica por contexto: time, produto, ecossistema, performance e manutenção.

Frameworks
Framework Quando usar O que dominar
Vue + Nuxt Times que já conhecem Vue, dashboards, produtos com curva de aprendizado amigável e necessidade de SSR/SSG no ecossistema Vue. Composition API, ref/reactive, computed, watchers, Vue Router, Pinia, Nuxt SSR, file-based routing, server routes e auto imports.
Angular Ambientes corporativos, produtos enterprise, necessidade de arquitetura rígida, DI, forms robustos, roteamento e convenções oficiais. Components, Signals, RxJS, services, dependency injection, reactive forms, guards, interceptors, lazy loading, standalone components, change detection e testes.
Svelte + SvelteKit Projetos em que performance, simplicidade, baixo boilerplate e bundle menor são prioridade. Compiler, stores/runes, SvelteKit routes, SSR, forms, load functions, actions e progressive enhancement.
Astro Blogs, documentação, landing pages, marketing sites, portfólios e conteúdo com alta exigência de performance. Content collections, Markdown/MDX, islands architecture, static generation, partial hydration, SEO e integrações.
Vite Build moderno para React, Vue, Svelte e vanilla TS, library mode e monorepos. Dev server, HMR, build, plugins, env vars, code splitting, library mode e integração com frameworks.

Decisão sênior

O melhor framework é o que reduz risco para o produto, melhora produtividade do time, atende requisitos de performance/SEO/acessibilidade/segurança e tem manutenção sustentável.

Estado, dados e arquitetura de aplicação

Separação entre estado de UI, servidor, formulário e rota.

State/Data
Tipo de estado Exemplos Ferramentas comuns Boas práticas
UI state Modal aberto, aba ativa, sidebar recolhida, dropdown. useState, useReducer, Context local. Manter perto do componente dono.

Cache invalidationDefinir quando dado expira, quando revalidar e como tratar concorrência.
Optimistic updatesAtualizar UI antes da confirmação e criar rollback seguro em caso de falha.
Real-timeUsar WebSocket/SSE quando há necessidade real de atualização contínua.
Contratos tipadosAlinhar frontend com backend/BFF via DTOs, schema validation e clients tipados.

Design System e UI Engineering

Tokens, componentes, documentação, acessibilidade e governança visual.

UI Engineering

Design system não é apenas biblioteca de componentes. É um contrato entre design, frontend e produto para acelerar entrega sem perder consistência, acessibilidade e qualidade.

Camada Conteúdo Entregável
Tokens Cores, tipografia, espaçamentos, radii, sombras, motion, z-index e breakpoints. Pacote versionado de tokens consumido por CSS, Tailwind, Storybook e Figma.
Componentes base Button, Input, Select, Checkbox, Radio, Dialog, Dropdown, Tabs, Tooltip, Toast, Table, DataTable, Pagination, Card, Sidebar, Navbar, Command Menu, Empty, Error e Skeleton. Biblioteca acessível, testada e documentada.
Estados Default, hover, focus, active, disabled, loading, error, success e empty. Stories e testes cobrindo variações críticas.
Governança Versionamento, breaking changes, changelog, guidelines, contribuição e review. Processo claro para evolução do design system.

Nível sênior

  • Criar componentes headless e compostos.
  • Definir component API sem props explosivas.
  • Projetar acessibilidade no componente base.
  • Garantir consistência visual em múltiplos produtos.
  • Documentar uso correto e anti-patterns.

Acessibilidade

WCAG, semântica, foco, teclado, leitores de tela, ARIA e testes contínuos.

A11y
Semântica primeiroUse elementos nativos corretos antes de adicionar ARIA.
TecladoToda funcionalidade deve operar sem mouse, com ordem de foco previsível.
FormuláriosTodo input precisa de label, erro identificado e instrução acessível.
Contraste e motionEstados visuais precisam de contraste, foco visível e respeito a reduced motion.
Área O que verificar Evidência
WCAG Critérios aplicáveis, contraste, navegação, labels, erros, foco e conteúdo dinâmico. Checklist de PR e auditoria periódica.
Leitor de tela Landmarks, nomes acessíveis, headings, tabelas, dialogs e live regions. Teste manual com NVDA/VoiceOver ou equivalente.
Automação axe, Testing Library, Playwright accessibility checks e CI. Falhas bloqueando merge quando críticas.
Componentes complexos Combobox, Dialog, Tabs, Tooltip, Dropdown, DataTable e modais. Stories com teclado e documentação de comportamento.

Erro comum

ARIA incorreto pode piorar a experiência. Prefira semântica nativa; use ARIA apenas quando necessário e com teste real.

Performance Web

Core Web Vitals, custo de JavaScript, imagens, fontes, cache e orçamento de performance.

Performance
Métrica/Tema O que mede Como melhorar
LCP Tempo até o maior conteúdo visível carregar. SSR/SSG quando fizer sentido, imagem correta, preload criterioso, cache e redução de TTFB.
INP Responsividade da página às interações. Reduzir trabalho na main thread, quebrar tarefas longas, evitar JS excessivo e handlers pesados.
CLS Estabilidade visual durante carregamento. Reservar dimensões de imagens/iframes, evitar inserir conteúdo acima e controlar fontes.
Bundle size Custo de JavaScript enviado ao browser. Code splitting, tree shaking, remover libs pesadas, dynamic import e análise de bundle.
Waterfall Ordem e dependência de requests. Preconnect/preload com critério, CDN, cache, lazy loading e evitar recursos bloqueantes.

Ferramentas

Lighthouse, WebPageTest, Chrome DevTools Performance/Coverage, Network waterfall, Bundle Analyzer e React Profiler.

Budget

Defina limites de JS, CSS, imagens, tempo de interação, LCP, INP e CLS por rota crítica.

Regra

Meça antes de otimizar. Otimização sem métrica vira opinião e pode trocar um gargalo por outro.

Testes Frontend

Estratégia de qualidade por risco: unit, component, E2E, visual, acessibilidade e contrato.

Qualidade
Camada Ferramentas O que testar Cuidados
Unitário Vitest/Jest Funções puras, formatadores, validações, reducers, hooks simples. Não testar implementação interna irrelevante.
Componente Testing Library, React Testing Library Renderização por role, user events, loading/error/empty/success, forms e acessibilidade básica. Priorizar queries que refletem uso real.
API mockada MSW Cenários de erro, timeout, dados vazios e respostas realistas. Mocks precisam representar contratos reais.
E2E Playwright/Cypress Jornadas críticas: login, checkout, CRUD, filtros, permissões e regressões importantes. Reduzir flakiness e manter suíte enxuta.
Visual/A11y Storybook, Chromatic, axe, Playwright Design system, variações visuais e estados acessíveis. Evitar snapshot sem critério.

Nível sênior

  • Montar pipeline com unit, component, E2E e accessibility tests.
  • Reduzir flakiness e tempo de execução.
  • Testar contrato com backend quando a integração for crítica.
  • Definir claramente o que não testar.
  • Usar Storybook para documentar e validar estados de componentes.

Segurança Frontend

XSS, CSRF, CORS, CSP, cookies, token storage, dependências e vazamento de dados.

Security
Risco Descrição Mitigação
XSS / DOM XSS Execução de script malicioso por entrada não confiável, HTML dinâmico ou manipulação insegura do DOM. Escape de output, sanitização, evitar dangerouslySetInnerHTML, CSP e revisão de dependências.
Token storage Tokens em LocalStorage são expostos a scripts em caso de XSS. Preferir cookie HttpOnly/SameSite/Secure quando a arquitetura permitir; entender trade-offs.
CSRF Ação autenticada disparada por outro site quando cookies são enviados automaticamente. SameSite, CSRF token quando necessário, validação de origem e desenho correto de sessão.
CORS Controle de quais origens podem ler respostas. Configuração explícita no backend/BFF, nunca usar wildcard com credenciais.
Segredos no bundle Env vars públicas, chaves ou tokens expostos no JavaScript enviado ao browser. Nunca colocar segredo no client; usar BFF/server para operações sensíveis.
Supply chain Pacotes vulneráveis ou comprometidos. Auditoria, lockfile, atualizações, revisão de dependências e CI.

Regra crítica

Esconder botão, link ou rota no frontend não é autorização. A autorização real precisa existir no backend/BFF e ser testada.

Arquitetura Frontend

Boundaries, modularidade, domínio, packages, BFF, microfrontends e ADRs.

Observabilidade Frontend

Error tracking, RUM, Web Vitals, analytics, correlação com backend e privacidade.

Observability
Área O que coletar Pergunta que responde
Error tracking Erros por versão, rota, navegador, usuário afetado e stack trace. Qual release quebrou e quais usuários foram impactados?
Web Vitals/RUM LCP, INP, CLS, TTFB, device, conexão, rota e geografia. A experiência real piorou após o deploy?
Tracing/correlation Correlation ID, trace propagation e ligação com backend. Qual request backend corresponde ao erro visto no frontend?
Analytics/funnel Eventos de produto, conversão, abandono e feature flags. A mudança técnica melhorou ou piorou o resultado de produto?
Privacidade Redação de dados sensíveis, consentimento e session replay com cuidado. Estamos coletando o mínimo necessário sem expor dados do usuário?

Nível sênior

Saber separar métrica técnica de métrica de produto, detectar regressão por versão, medir performance por rota e ligar erro frontend ao trace backend.

Conteúdo específico por framework

React + Next.js como trilha principal; Vue, Angular, Svelte e Astro como visão complementar.

Stack

React + Next.js como trilha principal

  • React, Hooks, Server Components, Client Components, Suspense, Error boundaries, Forms e Data fetching.
  • Next App Router, Metadata, SEO, Cache, Revalidation, Middleware, Auth, Cookies, Route Handlers, Streaming, Image optimization, Deploy, Observability e Testing.
  • Integração natural com projetos Next.js, Tailwind, shadcn/ui, dashboards, landing pages, blogs e produtos full stack.

Vue + Nuxt como trilha complementar

  • Vue Composition API, SFC, reactivity, watchers, computed, Vue Router, Pinia.
  • Nuxt SSR, file-based routing, server routes e auto imports.
  • Boa alternativa para times que priorizam curva de aprendizado e produtividade.

Angular como trilha enterprise

  • Components, standalone components, signals, services, DI, RxJS e reactive forms.
  • Guards, interceptors, lazy loading, Angular Material e testing.
  • Forte em ambientes corporativos que precisam de padrões rígidos e framework completo.

Svelte/SvelteKit e Astro

  • Svelte compiler, stores/runes, SvelteKit routes, SSR, forms, load functions, actions e progressive enhancement.
  • Astro com content collections, Markdown/MDX, islands architecture, static generation, partial hydration e SEO.
  • Excelente visão para performance, conteúdo, documentação e architectures com menos JavaScript.

Checklist de nível sênior

Critérios objetivos para considerar a trilha frontend em nível sênior.

Checklist
  • Explicar o funcionamento do navegador.
  • Criar HTML semântico e acessível.
  • Construir CSS escalável com design tokens.
  • Dominar JavaScript assíncrono e runtime.
  • Usar TypeScript para impedir estados inválidos.
  • Criar componentes React reutilizáveis, acessíveis e performáticos.
  • Projetar aplicações Next.js com SSR, SSG, cache e segurança.
  • Escolher framework por contexto.
  • Definir arquitetura de pastas e boundaries.
  • Criar design system documentado.
  • Medir e otimizar Core Web Vitals.
  • Criar estratégia de testes.
  • Proteger tokens, rotas e dados sensíveis.
  • Investigar bugs de hidratação, estado, renderização e performance.
  • Fazer code review técnico, ADRs e RFCs.
  • Mentorar devs júnior/pleno e comunicar trade-offs para backend, produto e design.

Fase Período Foco Entregável

7 Semanas 37–42 Design system, Storybook, tokens, componentes headless/compostos, testes visuais e governança. Design system documentado e versionável.
8 Semanas 43–48 Performance, segurança, observabilidade, arquitetura, CI/CD, BFF, ADRs, migração e portfólio final. Projeto sênior integrado ao backend com métricas, testes e documentação.
