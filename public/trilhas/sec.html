Resumo executivo

A segurança como competência central do desenvolvedor full stack moderno.

Visão geral

Segurança para full stack é a capacidade de construir sistemas que protegem dados, usuários, infraestrutura, integrações e cadeia de entrega. O desenvolvedor precisa entender como vulnerabilidades surgem no frontend, backend, banco de dados, APIs, cache, filas, cloud, containers e pipelines.

O foco desta trilha é desenvolvimento seguro defensivo: prevenir falhas, desenhar controles, validar permissões, reduzir superfície de ataque, automatizar verificações, observar comportamento em produção e responder a incidentes de forma organizada.

Regra central

O frontend pode melhorar a experiência, mas a segurança real precisa ser garantida no backend, no banco, na infraestrutura e no pipeline. Não confie em cliente, rede interna, payload externo, dependência, token ou configuração sem validação explícita.

Fundamentos indispensáveis

Conceitos que sustentam todas as decisões de segurança.

Nível básico
ConfidencialidadeSomente usuários, serviços e processos autorizados acessam dados. Exemplo: um usuário não vê pedidos de outro.
IntegridadeDados não podem ser alterados indevidamente. Exemplo: valor de pedido não vem confiável do frontend.
DisponibilidadeO sistema resiste a abuso, falhas e picos. Exemplo: rate limit evita queda por força bruta.

Classificação de dados

Tipo Exemplos Controles mínimos Erro comum
Público Post publicado, landing page, documentação pública. Integridade, disponibilidade e controle de alteração. Achar que dado público não precisa proteção contra alteração.
Interno Roadmap, documentação técnica, backlog, métricas internas. Autenticação, autorização e logs. Expor endpoints administrativos por descuido.
Sensível CPF, endereço, telefone, dados financeiros, dados pessoais. Minimização, criptografia, mascaramento e acesso restrito. Logar payload completo ou usar dump real em dev.
Confidencial Secrets, tokens, chaves, estratégia comercial, credenciais. Secret manager, rotação, auditoria e bloqueio de exposição. Subir .env ou chave no repositório.

Validação x sanitização x escaping

Controle Função Exemplo Onde aplicar
Validação Decide se o dado é aceitável. E-mail válido, tamanho máximo, enum permitido. Frontend para UX, backend para segurança, banco para constraints.
Sanitização Remove ou transforma conteúdo perigoso. Remover tags HTML não permitidas em comentário. Antes de armazenar/renderizar conteúdo rico.
Escaping Codifica saída conforme contexto. Escapar texto antes de inserir em HTML. Renderização no frontend ou template server-side.
Parametrização Separa comando de dado. Prepared statement em SQL. Consultas SQL/NoSQL/command execution.

Erro clássico

Validação no frontend nunca é suficiente. Usuários e scripts podem chamar a API diretamente, alterar payload, remover campos, forçar IDs, manipular headers e repetir requisições.

Senhas, login e tratamento seguro de erros

Como construir o primeiro fluxo crítico de qualquer sistema.

Login seguro

Login inseguro

  • Senha salva em texto puro ou SHA-256 puro.
  • Endpoint de login sem rate limit.
  • Mensagem diferencia “e-mail não existe” de “senha errada”.
  • Token sem expiração ou refresh token sem revogação.
  • Stack trace ou erro interno retornado ao cliente.
  • Senha, token ou payload de login gravado em log.

Login seguro

  • Hash com bcrypt ou Argon2, salt e custo adequado.
  • Resposta genérica para credencial inválida.
  • Rate limit por IP, usuário e/ou device fingerprint defensivo.
  • Access token curto e refresh token rotativo.
  • Auditoria de falhas e alertas para comportamento suspeito.
  • MFA para admin ou ações sensíveis.

Armazenamento de senha

Inseguro:
users.password = "123456"
users.password = sha256("123456")

Seguro:
users.password_hash = "$argon2id$v=19$m=65536,t=3,p=4$..."
users.password_hash = "$2a$12$..."

Spring Boot — exemplo conceitual

@Bean
PasswordEncoder passwordEncoder() {
    return new BCryptPasswordEncoder(12);
}

public void register(CreateUserCommand command) {
    String hash = passwordEncoder.encode(command.rawPassword());
    userRepository.save(new User(command.email(), hash));
}

public AuthResult login(LoginCommand command) {
    User user = userRepository.findByEmail(command.email())
        .orElseThrow(() -> new BadCredentialsException("Invalid credentials"));

    if (!passwordEncoder.matches(command.rawPassword(), user.passwordHash())) {
        throw new BadCredentialsException("Invalid credentials");
    }

    return tokenService.issueSession(user);
}

Erros seguros

Situação Retorno inseguro Retorno recomendado
Login falhou “E-mail existe, senha incorreta.” “Credenciais inválidas.”
Erro interno Stack trace, classe, linha e SQL. INTERNAL_ERROR + correlationId.
Acesso negado Detalhes internos da policy. 403 Forbidden com mensagem neutra.
Recurso privado “Pedido existe, mas não é seu.” 404 ou 403 conforme política definida.

Nível médio — segurança aplicada em projeto real

Controles que um dev full stack precisa aplicar em aplicações modernas.

Full Stack
Tema O que estudar Como aplicar Erro a evitar
JWT Assinatura, claims, exp, iss, aud, jti, algoritmo. Access token curto, validação completa e sem dados sensíveis no payload. Aceitar token apenas porque decodifica.
OAuth2/OIDC Authorization Code + PKCE, client credentials, ID token, access token. Usar IdP e scopes por API/recurso. Confundir OAuth2 com autenticação sem entender OIDC.
Cookies HttpOnly, Secure, SameSite, Path, Domain, Max-Age. Refresh token em cookie HttpOnly/Secure com rotação. Guardar refresh token no localStorage.
CORS Origin, credentials, methods, allowed headers, preflight. Allowlist por ambiente. origin: * com credenciais.
CSRF Cookies automáticos, token CSRF, SameSite, Origin/Referer. Proteger mutações quando autenticação usa cookie. Desabilitar CSRF sem avaliar o modo de autenticação.
XSS Stored, reflected, DOM XSS, CSP e sanitização. Escaping por contexto, evitar HTML bruto e aplicar CSP. Renderizar markdown/comentário sem sanitização.
Injection SQL, NoSQL, command, LDAP, template injection. Queries parametrizadas, DTOs, schema validation e allowlist. Concatenar SQL ou passar body direto para filtro Mongo.
Uploads MIME, magic bytes, tamanho, storage, scan, URL temporária. Validar conteúdo, renomear, isolar storage e limitar acesso. Confiar apenas na extensão do arquivo.
Logs Mascaramento, audit trail, correlationId, retenção. Log estruturado sem token/senha/secret. Logar payload completo de login/pagamento.

Segurança no frontend

Proteção no navegador, SPAs, SSR e frameworks como React/Next.js.

Client
Risco Causa comum Prática correta Prática incorreta
XSS HTML/Markdown externo renderizado sem controle. Sanitização, escaping, CSP e evitar dangerouslySetInnerHTML. Inserir conteúdo de usuário como HTML bruto.
CSRF Cookies enviados automaticamente em mutações. SameSite, CSRF token, checagem de Origin/Referer. Usar cookie auth sem estratégia CSRF.
Clickjacking Página embutida em iframe não confiável. CSP frame-ancestors e/ou X-Frame-Options. Sem header de frame em telas sensíveis.
Token theft Token sensível em localStorage/sessionStorage. Cookie HttpOnly para tokens sensíveis em muitos cenários. Refresh token em localStorage.
Exposição de secrets Variável pública no bundle. Somente chaves públicas em NEXT_PUBLIC_*. Colocar secret de API no frontend.
Autorização falsa Esconder botão sem proteger endpoint. Frontend melhora UX; backend autoriza de verdade. “Se o botão não aparece, está seguro.”

CSP inicial

Content-Security-Policy:
  default-src 'self';
  script-src 'self';
  style-src 'self';
  img-src 'self' data: https:;
  connect-src 'self' https://api.seudominio.com;
  frame-ancestors 'none';
  base-uri 'self';
  form-action 'self';

Next.js/React — checklist prático

  • Validar autorização em Server Components, Route Handlers, Server Actions e backend.
  • Não expor secrets em variáveis públicas ou HTML inicial.
  • Sanitizar conteúdo de CMS, Markdown, comentários e integrações.
  • Configurar headers de segurança no Next.js, gateway ou CDN.
  • Evitar armazenar dados sensíveis em localStorage, sessionStorage, IndexedDB ou logs do browser.
  • Tratar dados vindos da API como não confiáveis até serem validados/renderizados com segurança.

Spring Security — proteção por scope e recurso

@PreAuthorize("hasAuthority('SCOPE_orders:read')")
@GetMapping("/orders/{id}")
public OrderResponse getOrder(@PathVariable UUID id, Authentication auth) {
    return orderService.findAuthorizedOrder(id, auth.getName());
}

public OrderResponse findAuthorizedOrder(UUID orderId, String userId) {
    Order order = repository.findById(orderId)
        .orElseThrow(NotFoundException::new);

    if (!order.belongsTo(userId)) {
        throw new AccessDeniedException("Forbidden");
    }

    return mapper.toResponse(order);
}

Cuidado com logs

Nunca registre senha, access token, refresh token, secret, cookie completo, documento completo, cartão, payload de login ou dump de request sensível. Registre evento, usuário/subject, ação, recurso, resultado e correlationId.

Segurança em banco de dados

Controle de acesso, integridade, privacidade, backup e ambientes.

Dados
Tema Prática correta Erro comum Como validar
Privilégio mínimo Usuário por aplicação/serviço com permissões específicas. Aplicação usando superuser/admin. Revisar grants/roles e testar operação negada.
SQL Injection Prepared statements, ORM seguro, JPQL parametrizado. Concatenar parâmetro em SQL/JPQL. Testes com caracteres especiais e SAST.
NoSQL Injection Montar filtros explicitamente e validar schema. Passar req.body direto no filtro Mongo. Testes com operadores inesperados.
Criptografia TLS em trânsito, encryption at rest e KMS quando aplicável. Dados sensíveis em claro sem necessidade. Revisão de config e inventário de dados.
Backup Backup criptografado, retenção, acesso restrito e restore testado. Achar que backup existe sem restore. Drill de recuperação em ambiente separado.
Migrations Flyway/Liquibase, revisão, expand-contract e rollback planejado. Migration destrutiva sem plano. Subir ambiente do zero e rodar testes.
Dumps Anonimizar/pseudonimizar antes de usar fora de prod. Dump real em notebook local. Checklist LGPD e controle de descarte.

Mascaramento, anonimização e pseudonimização

MascaramentoExibir CPF como ***.***.***-12 ou e-mail como j***@dominio.com.
PseudonimizaçãoSubstituir identificador direto por token controlado e reversível sob política.
AnonimizaçãoRemover vínculo com pessoa natural de forma não reversível dentro do contexto.

Redis/cache seguro

Chave segura:
user:{tenantId}:{userId}:dashboard

Regras:
- TTL curto
- sem secrets no valor
- sem dados altamente sensíveis quando possível
- namespace por tenant/usuário
- Redis privado, com autenticação/TLS quando aplicável

Autenticação e autorização em profundidade

Onde muitas falhas críticas de aplicações modernas acontecem.

Identity
Conceito Função Exemplo Risco
Autenticação Provar identidade. Senha + MFA, OIDC, client credentials. Account takeover se fluxo for fraco.
Autorização Decidir acesso. Usuário pode ler apenas dados do próprio tenant. Broken Access Control/IDOR.
Access token Acessar API por curto período. JWT com exp, iss, aud, scopes. Token longo aumenta impacto de vazamento.
Refresh token Renovar sessão. Cookie HttpOnly, rotação, hash em banco. Roubo de refresh mantém acesso prolongado.
RBAC Permissão por papel. ADMIN, USER, MANAGER. Roles genéricas demais viram privilégio excessivo.
ABAC Permissão por atributos. Mesmo tenant, dono do recurso, status, departamento. Política complexa sem testes.
Scopes Permissões declaradas no token. orders:read, users:delete. Scope sem validação de recurso.
Claims Informações declaradas. sub, tenant_id, roles. Confiar em claim de token não validado.

IDOR — falha comum

Falha:
GET /api/invoices/100
GET /api/invoices/101
Usuário acessa fatura de outro cliente apenas trocando o ID.

Correção:
- Buscar por invoiceId + authenticatedUserId/tenantId
- Validar scope/role quando aplicável
- Auditar negações relevantes
- Retornar 404 ou 403 conforme política definida

Regra prática

JWT válido não significa acesso válido. O token identifica e carrega permissões gerais; o backend ainda precisa validar política de domínio, posse do recurso, tenant, escopo e estado do objeto.

OWASP aplicado ao desenvolvimento full stack

Como traduzir riscos OWASP em decisões de implementação.

OWASP
Risco Exemplo full stack Impacto Como detectar Como prevenir
Broken Access Control Usuário acessa pedido de outro alterando ID. Vazamento/alteração indevida. Testes por usuário, tenant, role e resource owner. RBAC/ABAC/scopes + validação no service/domínio.
Cryptographic Failures Senha sem hash, HTTP, dados sensíveis em claro. Vazamento crítico. Review, SAST e inspeção de config. TLS, bcrypt/Argon2, KMS e criptografia em repouso.
Injection SQL/NoSQL/command injection. Leitura, alteração ou execução indevida. SAST, testes de entrada, code review. Parametrização, ORM seguro, validação e allowlist.
Insecure Design Fluxo não prevê abuso ou fraude. Falha estrutural. Threat modeling e design review. Requisitos de segurança antes do código.
Security Misconfiguration CORS aberto, debug em prod, bucket público. Exposição ampla. IaC scanning, checklist e revisão de ambiente. Hardening, private by default e config por ambiente.
Vulnerable Components Lib npm/Maven com CVE explorável. Exploração conhecida. SCA, Dependabot, Snyk, Trivy. Atualização contínua, pinning e política de CVE.
Identification/Auth Failures Reset de senha fraco, token longo, sessão não revogada. Account takeover. Teste de fluxo auth e revisão de logs. MFA, token curto, rotação, revogação e rate limit.
Software/Data Integrity Failures Pipeline aceita artefato não confiável. Supply chain attack. Revisão CI/CD, assinatura, SBOM. Branch protection, provenance, assinatura e aprovação.
Logging/Monitoring Failures Incidente sem trilha de auditoria. Resposta tardia. Revisar logs, alertas e runbooks. Logs estruturados, SIEM e alertas acionáveis.
SSRF Backend acessa URL informada pelo usuário. Acesso a rede interna/metadados cloud. Review e testes controlados. Allowlist, bloqueio de IP interno e timeout.

OWASP ASVS como evolução

Depois de entender o Top 10, use OWASP ASVS como checklist verificável de requisitos de segurança. Ele ajuda a transformar boas práticas em critérios testáveis por nível de exigência.

Segurança em APIs REST e GraphQL

APIs são uma das superfícies mais exploradas em aplicações modernas.

APIs

REST

  • Autenticação em endpoints privados.
  • Autorização por recurso, tenant e scope.
  • DTOs separados para request/response.
  • Paginação limitada e filtros validados.
  • Rate limit em rotas públicas e críticas.
  • Idempotency-Key em operações sensíveis.
  • Erros com Problem Details e sem dados internos.
  • OpenAPI atualizado e testado.

GraphQL

  • Limitar profundidade e complexidade da query.
  • Aplicar autorização por resolver/campo/recurso.
  • Evitar introspection pública quando o risco justificar.
  • Bloquear overfetching de campos sensíveis.
  • Usar persisted queries em cenários críticos.
  • Rate limit por operação/custo, não apenas por request.
  • Monitorar queries lentas e padrões de abuso.

Endpoint seguro — checklist

Pergunta Resposta esperada
Quem pode chamar? Endpoint tem regra clara de autenticação e autorização.
Quais dados entram? DTO/schema valida tipo, tamanho, formato e enums.
Quais dados saem? Response não expõe campos internos ou sensíveis.
Como falha? Erros são padronizados, sem stack trace e com correlationId.
Como escala? Paginação, rate limit, timeout e limite de payload definidos.
Como audita? Ações sensíveis geram audit log com usuário, recurso e resultado.

Erro comum

Usar uma role ampla para “fazer funcionar” e nunca revisar depois. Em cloud, permissões amplas são uma das formas mais rápidas de transformar uma falha pequena em incidente grande.

Checklist de PR seguro

  • Endpoint exige autenticação quando necessário?
  • Autorização por recurso foi testada?
  • DTO evita mass assignment?
  • Inputs têm validação de tipo, tamanho e formato?
  • Há risco de injection?
  • Logs não expõem dados sensíveis?
  • Secrets não estão no código, Dockerfile ou pipeline?
  • Dependências novas são mantidas e sem CVE crítica?
  • Config de CORS/cookies/headers foi revisada?

Containers, Docker, Kubernetes e supply chain

Segurança da aplicação empacotada, implantada e distribuída.

Runtime

Docker seguro

  • Imagem base confiável e enxuta.
  • Multi-stage build.
  • Usuário não root.
  • .dockerignore correto.
  • Sem secrets na imagem ou build args.
  • Versões fixadas quando fizer sentido.
  • Imagem escaneada no pipeline.

Kubernetes seguro

  • RBAC mínimo por service account.
  • NetworkPolicies para tráfego interno.
  • Resource requests/limits.
  • Pod Security Standards.
  • Secrets com integração a secret manager quando possível.
  • Audit logs e admission policies.
  • Evitar container privilegiado e capabilities desnecessárias.

Modelo de ameaça prático

Fluxo Ameaça Controle Teste
Login Brute force, credential stuffing. Rate limit, MFA, lockout progressivo e alerta. Múltiplas tentativas e resposta 429.
Recurso privado IDOR/Broken Access Control. Autorização por recurso, tenant e scope. Usuário A acessa recurso de usuário B.
Upload Arquivo malicioso ou execução indevida. Validação, scan, storage isolado e URL temporária. Upload de MIME/extensão inválidos.
Webhook Evento falso, replay ou duplicidade. Assinatura, timestamp e idempotência. Replay de evento antigo/duplicado.
Serviço interno Chamada anônima entre serviços. mTLS, client credentials, audience por serviço. Serviço sem credencial chama API interna.
Cloud Role ou bucket permissivo. IAM mínimo, KMS, private by default e logs. Policy review e IaC scanning.

Defesa em profundidade

Não dependa de um único controle. Combine autenticação, autorização, validação, rate limit, WAF, logs, alertas, criptografia, IAM mínimo, segmentação de rede e resposta a incidentes.

Observabilidade, auditoria e resposta a incidentes

Segurança também depende de detectar, investigar e responder.

Fluxo de resposta a incidentes

1. DetectarAlerta, log, usuário, métrica, SIEM ou fornecedor informa comportamento suspeito.
2. ConterBloquear token, revogar secret, desativar rota, restringir IAM ou isolar workload.
3. Preservar evidênciaGuardar logs, horários, versões, artefatos e escopo afetado.
4. Corrigir causa raizPatch, configuração, validação, regra de acesso ou rotação de credenciais.
5. RecuperarDeploy, restore, reprocessamento, comunicação e monitoramento reforçado.
6. AprenderPostmortem, action items, testes regressivos e melhoria no pipeline.

Checklists práticos

Listas objetivas para revisar projetos reais antes de produção.

Execução

Frontend

Client
  • Não armazenar refresh token em localStorage/sessionStorage.
  • Evitar HTML bruto e sanitizar conteúdo externo.
  • Configurar CSP e proteção contra clickjacking.
  • Não expor secrets no bundle.
  • Validar no frontend só como UX, não como segurança única.
  • Checar autorização real no backend.

Backend/API

Server
  • Todo endpoint privado exige autenticação.
  • Autorização por recurso, tenant, role e scope.
  • Payload limitado e validado.
  • Queries parametrizadas.
  • Rate limit em endpoints críticos.
  • Erros padronizados e sem stack trace.

Auth/Authz

Identity
  • Senha com bcrypt/Argon2.
  • Access token curto.
  • Refresh token rotativo, revogável e armazenado como hash.
  • MFA para admin/ações sensíveis.
  • Testes de IDOR e escalação de privilégio.
  • Logout revoga sessão corretamente.

Banco e dados

Data
  • Usuário de banco com menor privilégio.
  • Sem dados reais em dev sem anonimização.
  • Backups criptografados e restore testado.
  • Migrations revisadas.
  • Dumps controlados e descartados.
  • Dados sensíveis minimizados e mascarados.

Deploy/cloud

Infra
  • HTTPS obrigatório e HSTS quando aplicável.
  • IAM mínimo.
  • Storage privado por padrão.
  • Secrets em manager.
  • Logs de auditoria cloud ativos.
  • Rollback e smoke test definidos.

CI/CD

Pipeline
  • Branch protection e PR obrigatório.
  • SAST, SCA e secrets scanning.
  • Container e IaC scanning.
  • Dependências atualizadas.
  • Build reproduzível.
  • Artefato rastreável, SBOM quando aplicável.

Checklist antes de produção

Revisar OWASP Top 10, autenticação, autorização por recurso, CORS, cookies, secrets, dependências, imagem Docker, variáveis de produção, logs, alertas, backup/restore, plano de rollback e runbook de incidente.
