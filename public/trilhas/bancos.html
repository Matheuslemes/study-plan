Resumo executivo

Banco de dados como competência central de backend pleno forte.

9ª trilha

Para um dev Java/Spring pleno forte, banco de dados não é apenas CRUD. O esperado é saber modelar, consultar, otimizar, integrar, proteger, observar e diagnosticar problemas de dados em produção.

A trilha prioriza PostgreSQL + MongoDB + Redis, adicionando DynamoDB pela trilha AWS. O objetivo é conectar banco de dados com JPA/Hibernate, APIs, microsserviços, Kafka, Outbox, Saga, CQRS, cache, observabilidade, backup, LGPD e decisões arquiteturais reais.

Performance

Conteúdo obrigatório de SQL

Consultas

  • SELECT, INSERT, UPDATE, DELETE.
  • WHERE, ORDER BY, GROUP BY, HAVING, LIMIT/OFFSET.
  • INNER JOIN, LEFT JOIN, RIGHT JOIN, FULL JOIN, self join e cross join.
  • Subqueries correlacionadas e não correlacionadas.
  • CTEs com WITH e CTEs recursivas em nível conceitual.
  • CASE WHEN, funções agregadas e funções de string/data.
  • Window functions: row_number(), rank(), dense_rank(), lag(), lead().

Modelagem

  • Chaves primárias, estrangeiras, únicas e constraints de domínio.
  • Relacionamentos 1:1, 1:N, N:N e tabela associativa.
  • Normalização: 1FN, 2FN, 3FN e BCNF conceitual.
  • Desnormalização controlada por padrão de leitura.
  • Soft delete, histórico, auditoria, versionamento e tabelas de domínio.
  • UUID vs ID sequencial e impacto em índice/ordenação.
  • Campos padrão: created_at, updated_at, deleted_at, created_by.

Exemplo de consulta com CTE, agregação e paginação

WITH post_stats AS (
  SELECT
    p.id,
    p.slug,
    p.title,
    p.published_at,
    COUNT(c.id) FILTER (WHERE c.status = 'APPROVED') AS approved_comments,
    COUNT(v.id) AS total_views
  FROM posts p
  LEFT JOIN comments c ON c.post_id = p.id
  LEFT JOIN page_views v ON v.post_id = p.id
  WHERE p.status = 'PUBLISHED'
  GROUP BY p.id, p.slug, p.title, p.published_at
)
SELECT *
FROM post_stats
WHERE published_at < :cursorPublishedAt
ORDER BY published_at DESC, id DESC
LIMIT :pageSize;

PostgreSQL em profundidade

Banco relacional principal para dominar no contexto Java/Spring.

PostgreSQL

Por que PostgreSQL

PostgreSQL entrega maturidade relacional, transações, constraints fortes, tipos avançados, JSONB, índices especializados, Full Text Search, particionamento, extensões e excelente encaixe com Spring/JPA.

O que saber na prática

Você precisa modelar tabelas, criar migrations, otimizar queries, ler planos, corrigir locks, desenhar índices, operar backup/restore e saber quando usar JSONB sem destruir o modelo relacional.

Índices recomendados no projeto de blog

-- Busca posts publicados por data
CREATE INDEX idx_posts_status_published_at
ON posts(status, published_at DESC)
WHERE status = 'PUBLISHED';

-- Slug único apenas para registros não deletados
CREATE UNIQUE INDEX uq_posts_slug_active
ON posts(slug)
WHERE deleted_at IS NULL;

-- Busca textual
CREATE INDEX idx_posts_search_vector
ON posts USING GIN(search_vector);

-- Comentários aprovados por post
CREATE INDEX idx_comments_post_status_created
ON comments(post_id, status, created_at DESC)
WHERE status = 'APPROVED';

-- Analytics temporal particionável
CREATE INDEX idx_page_views_post_viewed_at
ON page_views(post_id, viewed_at DESC);

EXPLAIN ANALYZE — rotina mínima

  • Compare linhas estimadas vs linhas reais.
  • Identifique Seq Scan inesperado em tabelas grandes.
  • Observe Nested Loop, Hash Join, Merge Join e custo de sort.
  • Verifique se índice composto está sendo usado na ordem correta.
  • Use BUFFERS para entender I/O quando necessário.
EXPLAIN (ANALYZE, BUFFERS)
SELECT p.id, p.title, p.slug
FROM posts p
WHERE p.status = 'PUBLISHED'
  AND p.published_at <= now()
ORDER BY p.published_at DESC
LIMIT 20;

JPA/Hibernate conectado ao banco real

O ponto onde muitos devs Java perdem performance sem perceber.

Java

Domínio obrigatório

  • Ciclo de vida da entidade: transient, managed, detached, removed.
  • Persistence context, dirty checking, flush e clear.
  • Lazy vs eager loading e consequências em API REST.
  • N+1 problem, fetch join, EntityGraph, projections e batch fetching.
  • JPQL, Criteria API, native query e DTO projection.
  • Cascade, orphan removal, relacionamento bidirecional e equals/hashCode.
  • Optimistic locking com @Version.
  • Pessimistic locking quando a concorrência exigir bloqueio real.

Spring Transaction

  • @Transactional no service, não como solução genérica em qualquer camada.
  • Propagation: REQUIRED, REQUIRES_NEW, SUPPORTS, MANDATORY, NOT_SUPPORTED, NEVER, NESTED.
  • Isolation: READ_COMMITTED, REPEATABLE_READ, SERIALIZABLE.
  • Rollback rules para checked/unchecked exceptions.
  • Transações longas e impacto em locks/conexões.
  • Lazy loading fora da transação e riscos de Open Session in View.
  • HikariCP: pool size, leak detection, idle timeout, max lifetime e saturação.

Exemplo: EntityGraph para evitar N+1

@EntityGraph(attributePaths = {"author", "category", "tags"})
Optional<Post> findBySlugAndStatus(String slug, PostStatus status);

Exemplo: lock otimista

@Entity
public class ProductStock {
    @Id
    private UUID id;

    private Integer availableQuantity;

    @Version
    private Long version;

    public void reserve(int quantity) {
        if (quantity <= 0) throw new IllegalArgumentException("quantity must be positive");
        if (availableQuantity < quantity) throw new InsufficientStockException();
        this.availableQuantity -= quantity;
    }
}

NoSQL pragmático

Escolher NoSQL por padrão de acesso, não por moda.

NoSQL

Princípio central

NoSQL não significa “sem regra”. Significa que a modelagem deixa de ser puramente relacional e passa a ser orientada por padrão de acesso, volume, latência, consistência, distribuição e custo operacional.

TipoExemploUse quandoEvite quando
DocumentoMongoDBDados agregados, flexíveis, lidos juntos, com estrutura variável.Precisa de muitas transações relacionais e joins fortes.
Chave-valorRedis, DynamoDBBaixa latência, cache, sessão, contadores, acesso por chave.Precisa de consultas ad hoc complexas.
Coluna largaCassandraAlta escala, escrita massiva, query-first design.Precisa de consistência forte e consultas flexíveis.
BuscaElasticsearch/OpenSearchFull-text search, logs, agregações, ranking e analytics.Precisa de transação OLTP como fonte primária.
GrafoNeo4j, NeptuneRelações complexas, recomendação, caminhos, conexões.Dados são simples e tabulares.

Trade-offs que você precisa explicar

  • Consistência forte vs consistência eventual.
  • Duplicação controlada vs normalização.
  • Baixa latência vs flexibilidade de consulta.
  • Escala horizontal vs complexidade operacional.
  • Modelagem por leitura vs modelagem por escrita.
  • Transação local vs transação distribuída/compensação.

MongoDB

Documento, agregados, índices e modelagem orientada a padrão de acesso.

Document DB

Fundamentos

  • Database, collection, document, BSON e _id.
  • CRUD, filtros, projections, sorting, paginação, update operators e upsert.
  • Embedded documents, arrays, validação de schema e versionamento de schema.
  • Bulk writes, write concern, read concern e retryable writes.

Modelagem

  • Embed quando os dados são lidos juntos e têm ciclo de vida parecido.
  • Reference quando dados crescem muito, são compartilhados ou têm ciclo próprio.
  • Evitar arrays infinitos e documentos com crescimento sem limite.
  • Duplicar dado com critério quando o padrão de leitura exigir baixa latência.
  • Modelar pela pergunta que a aplicação faz, não por um DER relacional.

Exemplo de aggregation

db.posts.aggregate([
  { $match: { status: "PUBLISHED" } },
  { $unwind: "$tags" },
  { $group: { _id: "$tags", total: { $sum: 1 } } },
  { $sort: { total: -1 } },
  { $limit: 20 }
]);

Operação MongoDB

  • Replica set: primary, secondary, election e failover.
  • Read preference e write concern.
  • Sharding: shard key, chunks, balancer e hot shard.
  • Slow queries, explain, profiler, métricas e Atlas.
  • Backup/restore e retenção.

Redis

Cache, rate limiting, locks, streams e estruturas rápidas.

In-memory

Estruturas

String, Hash, List, Set, Sorted Set, Bitmap, HyperLogLog, Stream e TTL.

Cache

Cache-aside, write-through, TTL, eviction, stampede, warming e invalidation.

Produção

Persistence, replication, Sentinel, Cluster, memory policy, slowlog, ACL e TLS.

Estratégias de cache

EstratégiaComo funcionaRiscoUso recomendado
Cache-asideAplicação busca no cache; se miss, busca no banco e popula cache.Cache inconsistente se não invalidar.Leitura pública de posts, categorias, tags.
Read-throughCache carrega dados da fonte.Acoplamento ao cache provider.Cenários com camada de cache dedicada.
Write-throughEscrita atualiza cache e banco no mesmo fluxo.Maior latência de escrita.Dados lidos com muita frequência.
Write-behindEscrita vai para cache e persiste depois.Perda de dados se falhar.Somente quando perda/tolerância for aceitável.
Stale-while-revalidateServe valor antigo e atualiza em background.Dado temporariamente desatualizado.Conteúdo público com tolerância a atraso.

Problemas clássicos de cache

  • Cache stampede: muitos requests recalculam o mesmo valor após expiração.
  • Cache penetration: consultas repetidas a chaves inexistentes atingem o banco.
  • Cache avalanche: muitas chaves expiram ao mesmo tempo.
  • Hot key: uma chave concentra tráfego e satura Redis.
  • Invalidação incorreta: dado antigo permanece após update.

Redis Streams

  • Append-only log para eventos leves.
  • Consumer groups, pending entries, ack, retry e dead-letter stream.
  • Não substitui Kafka em cenários de streaming robusto, mas resolve filas internas simples.

DynamoDB

NoSQL chave-valor/documento gerenciado da AWS para cenários serverless e alta escala.

AWS

Conteúdos essenciais

  • Table, item, attribute, partition key e sort key.
  • GSI, LSI, sparse indexes e overload de índice.
  • Single-table design e access patterns.
  • Strongly consistent read vs eventually consistent read.
  • Conditional writes, optimistic locking e transactions.
  • TTL, Streams, DAX, capacity modes e throttling.
  • Hot partitions e desenho de chave para distribuição.

Quando usar

  • Baixa latência por chave em escala alta.
  • Aplicações serverless com Lambda/API Gateway.
  • Eventos, sessão, preferências, histórico simples, idempotency keys.
  • Quando o padrão de acesso é conhecido antes da modelagem.
  • Quando operação gerenciada e escalabilidade são mais importantes que query flexível.

Arquitetura de dados em sistemas distribuídos

Como banco conversa com microsserviços, Kafka e consistência eventual.

Arquitetura

Database per service

Evita acoplamento entre microsserviços, mas exige eventos, APIs, read models e estratégia de consistência. O contrário, shared database, tende a criar dependência forte e deploys acoplados.

Consistência eventual

Em sistemas distribuídos, nem tudo precisa ser transação forte. O importante é saber onde aceitar atraso, como compensar falhas e como tornar consumidores idempotentes.

Padrões obrigatórios

PadrãoProblema que resolveComo aplicar
Transactional OutboxGarantir persistência do dado e publicação de evento sem transação distribuída.Salvar entidade + evento na tabela outbox na mesma transação; worker publica no Kafka.
SagaFluxo distribuído com múltiplos serviços e compensações.Orquestração ou coreografia para pedido, pagamento, estoque e entrega.
CQRSSeparar leitura otimizada de escrita transacional.Comandos alteram modelo transacional; eventos atualizam read models.
Event SourcingEstado derivado de histórico de eventos.Use com critério em domínios auditáveis e complexos.
CDCCapturar mudanças do banco para eventos.Debezium + Kafka para propagar alterações.
Idempotent ConsumerEvitar duplicidade com mensagens repetidas.Guardar chave de processamento e ignorar reprocessamento duplicado.
Materialized ViewLeitura rápida para consulta agregada.Atualizar via job, evento ou refresh controlado.

Exemplo Outbox

CREATE TABLE outbox_events (
  id UUID PRIMARY KEY,
  aggregate_type VARCHAR(80) NOT NULL,
  aggregate_id UUID NOT NULL,
  event_type VARCHAR(120) NOT NULL,
  payload JSONB NOT NULL,
  status VARCHAR(30) NOT NULL DEFAULT 'PENDING',
  created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT now(),
  published_at TIMESTAMP WITH TIME ZONE
);

CREATE INDEX idx_outbox_status_created
ON outbox_events(status, created_at)
WHERE status = 'PENDING';

Operação, segurança e observabilidade

O que diferencia um dev que usa banco de um dev que opera banco com responsabilidade.

Produção

Observabilidade

Slow queries, locks, deadlocks, pool, latency, cache hit ratio, replication lag, CPU, I/O e dashboards.

Segurança

Least privilege, roles, grants, secrets, TLS, encryption, audit logs, masking, LGPD e injection prevention.

Recuperação

Backup, restore testado, PITR, snapshots, RPO, RTO, failover, DR drill e runbooks.

Checklist de segurança

  • Usuário de aplicação com menor privilégio.
  • Credenciais fora do código e com rotação planejada.
  • Prepared statements e parametrização contra SQL injection.
  • Validação de input contra NoSQL injection.
  • TLS em trânsito e criptografia em repouso quando aplicável.
  • Audit log para ações sensíveis.
  • Masking/anonymization para dados pessoais em logs e ambientes não produtivos.
  • Política de retenção, exportação e exclusão de dados conforme LGPD.

Roadmap integrado às 8 fases

Progressão da trilha Banco de Dados dentro do cronograma de 64 semanas.

64 semanas

Fase 1 — SQL e modelagem relacional

Sem 1–8

Objetivo: construir base relacional sólida para APIs Java/Spring.

  • SQL básico/intermediário, joins, constraints, normalização e modelagem ER.
  • PostgreSQL básico: tipos, tabelas, chaves, índices simples e transações.
  • Flyway migrations e convenções de nomenclatura.
  • Entregável: DER do blog + migrations iniciais + seed local.

Fase 2 — JPA/Hibernate + transações

Sem 9–16

Objetivo: conectar banco real com Spring sem cair em antipadrões.

  • Entidades, relacionamentos, lazy/eager, dirty checking e flush.
  • @Transactional, propagation, isolation, locking e HikariCP.
  • N+1, EntityGraph, projections, batch fetching e paginação.
  • Entregável: API com Testcontainers e queries otimizadas.

Fase 3 — Performance SQL

Sem 17–24

Objetivo: diagnosticar e corrigir gargalos reais de banco.

  • Índices compostos, parciais, funcionais, GIN/BRIN e seletividade.
  • EXPLAIN ANALYZE, scans, joins, sort, buffers e estatísticas.
  • CTEs, window functions, materialized views e query rewrite.
  • Entregável: relatório antes/depois de tuning.

Fase 4 — MongoDB

Sem 25–32

Objetivo: modelar documentos corretamente para padrões de leitura/escrita.

  • Documentos, BSON, embed vs reference e schema validation.
  • Índices, aggregation, transactions, replica set e sharding conceitual.
  • Spring Data MongoDB e testes com Testcontainers.
  • Entregável: módulo de documentos/snapshots com MongoDB.

Fase 5 — Redis

Sem 33–40

Objetivo: usar Redis com estratégia, não como cache aleatório.

  • Estruturas de dados, TTL, eviction, persistence e monitoramento.
  • Cache-aside, invalidation, stampede, locks e rate limiting.
  • Redis Streams, consumer groups e DLQ simples.
  • Entregável: cache + rate limit + lock distribuído documentado.

Fase 6 — Dados em microsserviços

Sem 41–48

Objetivo: desenhar consistência em sistemas distribuídos.

  • Database per service, Outbox, Saga, CQRS, Event Sourcing e CDC.
  • Idempotência, duplicidade de mensagens, DLQ e compensação.
  • DynamoDB: access patterns, PK/SK, GSI, TTL, Streams e hot partitions.
  • Entregável: outbox + Kafka + read model.

Fase 7 — Operação e segurança

Sem 49–56

Objetivo: operar banco com responsabilidade de produção.

  • Backup/restore, PITR, RPO/RTO, DR drill e runbooks.
  • Observabilidade: slow queries, locks, pool, cache hit, replication lag.
  • Segurança: least privilege, TLS, secrets, audit log, LGPD e masking.
